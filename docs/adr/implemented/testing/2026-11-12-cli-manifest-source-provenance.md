# ADR: The CLI consumer is proved by source provenance, not by a recorded bundle digest

Status: implemented — the manifest records what the CLI build can honestly reproduce; the missing bundle digest is the decision, not a gap to close.

Date: 2026-11-12

Scope: the `cli`, `dsh`, `engine`, `omp` and `opencode` entries of `scripts/execution-consumer-manifest.ts` and the `scripts/packaging-manifests/*.json` they produce.

## Problem

The consumer manifest promised a byte pin on every consumer's build output. For the CLI that promise was never true: `packages/cli/dist/mstar-harness.js` is one bundle produced from the same committed tree, and it comes out with different bytes across checkouts. The root cause is unreproduced, and the recorded digest therefore describes the machine that ran the build rather than the source it came from. A pin that no reproducible procedure can re-derive fails for the wrong reason: it reports environment drift as source drift, and the only repairs available are re-pinning whatever the current machine produced (which re-establishes nothing) or deleting the check. Neither is evidence. The manifest also enforced two structural assumptions that existed only to serve byte pinning — every consumer must record a non-empty generated set, and the entrypoint must be a member of it — so a consumer that honestly cannot pin its bundle could not say so.

## Decision

- The manifest records, per consumer, the deterministic closure that consumer can honestly pin. For the CLI that is its source closure (source trees, config and build-script files) plus its runtime floor and capability; the generated closure is empty.
- `packages/cli/dist/mstar-harness.js` is excluded from the CLI's dist tree digest and declared as no generated file. The consumers whose build output is not reproducible (`cli`, `dsh`, `engine`, `omp`, `opencode`) record no generated bytes for the same reason: their `dist` bytes depend on the build environment, and a manifest written on one machine cannot be verified on another. `zcode` is the only consumer that still pins generated bytes, because its hook is committed rather than built.
- An empty generated closure is a legitimate state, not a missing build. The producer and the checker both refuse an empty generated tree or artifact only when the layout declares generated files, so a layout that pins nothing cannot smuggle in an unbuilt tree, and one that pins bytes still refuses when they are absent.
- The entrypoint is proved by existence and non-emptiness on both sides, without a digest. A consumer that records no generated bytes still cannot ship a missing or empty surface.
- The dsh `client.js` precedent — exclude the artifact, then re-derive it byte-identically from a declared producer — is deliberately not copied. This repository bans byte-equality assertions, so a re-derivation proof would be a second, weaker pin of the same environment-dependent value.

## Alternatives considered

- **Keep the bundle pinned and re-record it on every build.** Rejected: re-pinning records the builder, not the source, and turns every unrelated environment difference into a failing check with no actionable cause.
- **Delete the CLI consumer entirely.** Rejected: it would discard the pins that are honest and deterministic — the source closure and the runtime floor — to remove one that is not.
- **Copy the dsh re-derivation shape.** Rejected: it requires a byte-identical rebuild assertion, which this repository prohibits, and it would claim reproducibility for a bundle whose byte variance is exactly what is unexplained.
- **Add a manifest field for unpinned entrypoints.** Rejected: the existing shape already expresses it — an empty generated set, plus the entrypoint that the check proves separately — and a new field would be a second way to say the same thing.

## Consequences

- A change to the CLI bundle's bytes is not manifest drift. What CI still catches for this consumer is a changed source input, a changed runtime floor, a changed capability, and a missing or empty entrypoint.
- A defect that only manifests as different bundle bytes — a rebuild that loses the ASCII escaping, say — is caught by the CLI's own build and its consumers' tests, not by this manifest. That is the cost of the decision and the reason the bundle stays a required artifact.
- The `zcode` consumer keeps its byte pin, so its drift still fails with the offending consumer and entry named; the other five are proved by their source closures and entrypoint existence.
- Reinstating the pin is a deliberate act: it requires explaining the byte variance first, because a digest recorded without that explanation is what this record refuses.
