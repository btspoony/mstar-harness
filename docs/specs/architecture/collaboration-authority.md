# Architecture: collaboration authority

## Scope

This page describes the collaboration domain — issues and findings, their occurrences, transitions, relations and provenance, projects and their provider bindings, roadmaps, milestones, and portable catalog identity — and the one user-level SQLite database per canonical repository that owns it. It covers identity and mode selection, the staged-to-active lifecycle, the cutover that moves a legacy combined store out, read completeness and consumer evidence, the two receipts of a cross-domain operation, and backup/restore boundaries.

Execution state (workflows, plans, sessions, leases, coordinator bindings, projections, host state) stays in the control checkout's `{HARNESS_DIR}/store.db` and is described in [store-authority.md](store-authority.md). Tracked document bodies and catalog registration are described in [document-corpus.md](document-corpus.md). The ADRs under `docs/adr/` fix why the domains were split and where provider I/O lives; this page states only the implemented behavior, including the implemented `remote` selection and its verified private cache.

## Current state

### Identity, mode and location

`resolveCollaborationLocation` derives a canonical repository key, the configured mode, and the database path. It reads Git and `.mstarc`; it opens no database and creates no SQLite store directory, so an uninitialized scope is still disclosed. Its only write is local evidence: an origin-backed checkout records the selector commit it observed in `{HARNESS_DIR}/collaboration-selector-observation.json` before that observation can be used, so a later deletion of the ref is never read as a checkout that never saw one. Recording that evidence creates the missing `{HARNESS_DIR}` directory when it does not exist yet; it never creates the repository's storage directory or a lane.

- **Configuration.** `.mstarc` carries a `[collaboration]` section: the header alone on its line, then `mode=local`, `mode=mirror` or `mode=remote`, and `repo_id` only for a genuinely origin-less repository. A minimal declaration is:

  ```ini
  [collaboration]
  mode=local
  ```

  The parser reads `key=value` lines inside the section, so an inline `[collaboration] mode=local` written on one line leaves the mode unset and refuses `collaboration.mode-required`. The main checkout supplies both the origin and the `.mstarc` value; a linked worktree cannot answer as its own repository. The legacy normalized repo/author marker is not a storage key and is not re-encoded. Per-project provider identity keeps its existing `project_bindings` rows and `[linear]` semantics.
- **Origin canonicalization.** Portable `https://`, `http://`, `ssh://` and SCP SSH (`[user@]host:path`) origins are accepted. Userinfo is discarded, the DNS host lowercased with one terminal dot stripped, a scheme-default port elided and any other port retained as `host~port`. One terminal `.git` and trailing slashes are stripped; GitHub owner/repository path segments are lowercased while other hosts keep their case; nested owner segments are preserved. A query or fragment, a literal or percent-encoded dot segment, a backslash, an ASCII control character, an unsafe path segment, a non-portable transport, or several disagreeing fetch origins refuse `collaboration.repo-identity-unresolved`. Git unreadable is a refusal, never an origin-less checkout.
- **Key and path.** With an origin the key is `host/owner/repo` and the database is `<user home>/.mstar/repos/<host>/<owner>/<repo>/collaboration.db`. Without an origin the logical key is `id:<repo_id>` (`[a-z0-9][a-z0-9._-]*`, at most 128 characters) but the storage directory is the reserved `_id` rung: `<user home>/.mstar/repos/_id/<repo_id>/collaboration.db`, never an `id:` directory. Directory segments carry the same filesystem spelling rules: uppercase ASCII is percent-encoded so case-insensitive filesystems keep distinct repositories apart, and a segment spelling a reserved authority basename (`collaboration.db`, `-wal`, `-shm`, `-journal`) is escaped. Every existing component of that tree is inspected without following a link and must carry no group/other permission bits; a symlinked or redirected component, or a target outside the private root, is `collaboration.unreadable`.
- **Modes.** `local` and `mirror` select the same user-level database as the authority. `mirror` adds only the pre-existing one-way host-owned Linear delivery: the local database remains authoritative, a local commit and a confirmed delivery are separate outcomes, and importing remote observations never mutates local authority. `remote` selects the verified provider project set named by the protected Git selector; this checkout's database is then only a verified observation cache and intent ledger (`remote_bindings`, `remote_observations`, `remote_issue_identities`, the v3 `remote_outbox`/`remote_outbox_receipts` pair, and a schema-versioned `collaboration-remote-cache` inventory), never authority, and local issue/catalog/ledger rows are never read or served for it. Selection, `remote bind`, `remote observe`, `remote status`, `remote adopt-issue`, the ordinary remote writers and the durable outbox below are implemented; provider transport and any remote round-trip are not, and no command opens a provider connection. A missing mode is `collaboration.mode-required`, an unknown one `collaboration.mode-invalid`, an unreadable `.mstarc` (symlink, directory, unreadable file) `collaboration.config-unreadable`. Editing mode never relocates or rebinds a live authority. Every origin-backed checkout resolves only from a live lookup of `refs/heads/mstar-collaboration-authority` at its canonical origin: a successful absence leaves `local`/`mirror` on their own lane, a present selector is fetched and re-checked as the same commit, and a failed lookup is `remote.selector-unavailable` rather than absence. A `draining` selector therefore stops `local`/`mirror` writers with `collaboration.stale-binding`.

### Database and lifecycle

The lane is an independent SQLite database with its own `schema_version` ledger and three immutable, additive migrations: `collaboration-core` (version 1), `collaboration-remote-cache` (version 2, which rebuilds `collaboration_meta` with `remote` added to the mode check, adds the unique `issues.issue_ref` and backfills one stable reference per existing issue, and adds `remote_bindings`, `remote_observations` and `remote_issue_identities`), and `collaboration-remote-outbox` (version 3, which adds `remote_outbox` and `remote_outbox_receipts`). Admission is strict: the closed table inventory and each table's required columns must match this build exactly, and the single `collaboration_meta` row must be well formed. A missing table, an unexpected table, a lost column, a corrupt header, or an unsupported schema refuses `collaboration.unreadable` instead of admitting a handle whose queries would fail later. Bounded contention is the shared `store.busy`; an unsupported runtime or schema passes through as `store.runtime-unsupported` / `store.schema-unsupported`.

A lane recorded at a version this build does not admit is not served by an ordinary read, write or `store init`: each refuses `collaboration.upgrade-required` and names the one explicit upgrade. Fresh initialization applies every supported migration in order before publication, and a remote checkout's cache lane is created complete by the reviewed `remote bind`.

`collaboration_meta` carries `repository_key`, `mode`, `store_id`, `authority_state`, `authority_epoch`, `revision` and `catalog_revision`. The domain tables are `issues`, `issue_counter`, `occurrences`, `issue_transitions`, `relations`, `provenance`, `issue_project_moves`, `project_bindings`, `project_roadmaps`, `project_milestones`, `issue_sync_state`, `sync_cursor`, `sync_runs`, `catalog_entities`, `catalog_links`, `catalog_operations`, the effect ledger `collaboration_operations`, and the publication ledger `cutover_publications`. Execution-side catalog pins stay in the execution store's `catalog_execution_bindings`.

States and their codes:

- **Missing** — no database at the resolved path: `collaboration.not-initialized`. Nothing is created by a read.
- **Staged** — a complete, verified database whose `authority_state` is `staged`: `collaboration.not-active`. Only the cutover's stage inspection, adoption's lineage check, and the backup/restore validators open it; it is never runtime business data.
- **Active** — the published generation the runtime reads and writes.
- **Unreadable** — present but invalid, corrupt, inaccessible, or foreign: `collaboration.unreadable`.
- **Stale binding** — the checkout's recorded binding, the database's recorded key/mode, or an expected `store_id`/`epoch` disagrees: `collaboration.stale-binding`.

`initializeCollaborationStore` is create-only. A missing database is built complete in a private staging directory whose file carries the reserved basename, verified as this build's own store, folded into one self-contained file, and published with one create-only hard link; a matching record already on disk is reused without clearing it, and a record for another repository, mode, state, store id or schema refuses. Two initializers racing on one scope settle on the first published record.

### Bootstrap, binding and adoption

`store init` and `store upgrade` establish the repository's collaboration authority **before** the execution half reports anything: the lane is created or reused (never cleared), and a freshly created empty staged lane becomes this scope's first active generation. A combined store that still holds collaboration rows is not a fresh scope and refuses with `collaboration.cutover-required`.

`mstar store upgrade --operator <name>` is also the explicit in-place schema upgrade: an admitted version-1 lane runs the full v1→v3 ladder in one `BEGIN IMMEDIATE` (the checkout's finalized binding must name the lane's exact `store_id`/`epoch` first, then re-read the ledger, prove each recorded predecessor checksum against this build's immutable body and the exact v1 layout, apply the v2 `collaboration-remote-cache` DDL with the `issue_ref` backfill and append exactly one ledger row for it, prove the resulting v2 shape, apply the v3 `collaboration-remote-outbox` DDL and append exactly one ledger row for it, then verify the current layout, record the operator's `collaboration_operations` upgrade receipt and re-prove the checked selector before commit), so its issue history survives with one stable reference per issue. Repeating the verb revalidates and commits nothing more. The upgrade result names the collaboration receipt (`fromVersion`, `toVersion`, `issuesBackfilled`) in its envelope; a lane it cannot verify — including one this checkout is not bound to, or one whose selector moved under the migration lock — refuses without modification.

Each control checkout's ownership of one generation is recorded in `{HARNESS_DIR}/collaboration-binding.json` (key, mode, store id, epoch, state). A `claim` row is attempt-scoped evidence that readers ignore; `active` is the finalized binding. Consequences:

- A checkout that resolves a different repository key or mode than its active binding refuses `collaboration.stale-binding`; an origin or `.mstarc` change never re-points a bound checkout.
- A checkout with **no finalized binding** may read the resolved authority (a replacement clone reads before it is bound) and the read writes nothing; every write refuses until the checkout is bound. `store init` never adopts an active authority, so `mstar store collaboration adopt --harness <abs> [--expect-store <store-id>]` is the only supported acquisition: it verifies the canonical scope, the lane metadata and the recorded publication lineage (cutover publication, restore or file-era activation row) for the exact live store **and** epoch, writes nothing but this checkout's binding, is idempotent for the same binding, and refuses a staged authority, a foreign checkout, a missing/ambiguous/mismatched lineage, or a claim naming another generation.
- A **bound** checkout admits only the generation it recorded: a different key, mode, store id or epoch refuses `collaboration.stale-binding` for reads and writes alike, so a replacement generation published at the same key and mode is adopted deliberately, never read by drift.

**Local/mirror to remote.** A lane the repository already published as `local`/`mirror` is retired only by the reviewed transition: the checked *active* selector must supersede a `local`/`mirror` generation as its `previous` and carry a `cutover` with `sourceFenced: true` and no pending operation. `remote bind` then proves the canonical lane is exactly the checkout's recorded predecessor (key, mode, store id, epoch) inside a `BEGIN IMMEDIATE`, re-proves the checked selector immediately before the rename under the same operator exclusion, renames it to `collaboration.retired-<storeId>-<epoch>.db` beside itself, and only after that creates the verified cache and publishes the v3 binding. The retired rows stay readable to no runtime path; a crash after the rename replays from the preserved image, while a missing predecessor or unfenced/foreign lane refuses without touching any bytes. A recorded v3 generation is superseded the same way and never replaced because its private cache vanished: a missing cache does not substitute for the checkout's recorded selector lineage.

### Cutover from a combined store

An unfenced execution store that still holds collaboration rows is a legacy owner. Runtime reads, `store init`, `store upgrade` and a restore all refuse it with `collaboration.cutover-required`; the reviewed cutover hands that authority on. The runtime fence probe reads the execution file directly, so damaged execution metadata cannot hide readable legacy collaboration rows, while an absent execution store or one that holds no collaboration rows leaves the lane usable. An execution file that cannot be inspected at all refuses (`collaboration.unreadable`) for an **unbound** checkout, whose ownership is unproven; a **bound** checkout was adopted, so that file is left to the execution domain's own `store.corrupt`/`store.busy` instead of being reported as a collaboration refusal.

`mstar store collaboration plan --harness <abs> --out <abs>` inspects the source read-only and writes a manifest: `version`, `manifestId` (a digest of the body), the frozen source stamp (`storeId`, `epoch`, `schemaVersion`, `revision`, `catalogRevision`), the source digest and row counts, the resolved `repoKey`/`mode`, and `blockers`. Blockers are an open mirror run (`sync_runs` row) or a catalog journal entry not yet `committed`; they are reported as `collaboration.cutover-not-quiescent` and never guessed away. The verb creates nothing else.

`mstar store collaboration apply --harness <abs> --manifest <abs>` re-derives the manifest digest (a hand-edited manifest is refused), re-checks the scope, refuses a non-empty blocker list, and stages a verified copy of the frozen rows into the canonical target under the source write lock. An identical staged receipt is reused; a target that progressed past verification, or a source already fenced, is never restaged.

`mstar store collaboration activate --harness <abs> --manifest <abs> --operator <name> --attestation <abs>` is the only publication step. It validates the operator's full `ActivationAttestation` — including its `cutover` block naming the exact `repoKey`, `mode`, control root, source store/epoch/schema, the stopped handles and `allHandlesStopped`, bound to the running build, with no generated self-attestation — then, in one source transaction under SQLite write exclusion: re-reads the snapshot and blockers, takes or verifies the retained pre-fence image, commits the fence ledger row in the execution store's `collaboration_cutover`, drops the moved collaboration tables from the source (their rows survive only in the verified pre-fence image), and advances the execution schema. After that it makes the target active and commits its `cutover_publications` row and this checkout's binding together.

- **Lock.** `plan`, `apply`, `activate` and the durable fence step hold one local OS lock at `{HARNESS_DIR}/collaboration-cutover.lock` for the whole critical section. Exclusive create carries `{pid, host, startedAt, token}`; a same-host dead pid is recoverable through a serialized recovery slot, and a live or foreign-host holder refuses with a named recovery. There is no elapsed-time takeover.
- **Crash and replay.** A crash before the fence leaves a restageable attempt. A crash after the fence but before publication is finished by re-running the same `activate`, which reuses the persisted fence and commits only the missing publication. A staged slot and the publication serialize on the canonical target, so two clones cannot both fence under competing manifests (`collaboration.cutover-conflict`). An uncertain fence outcome is `collaboration.cutover-unconfirmed`: inspect the persisted fence record, the pre-fence image and the source's schema, and never retry blindly or claim the source is unchanged. There is no auto-rollback and no guessed merge.

### Read completeness and consumer evidence

Every view returns a `ReadEnvelope<T>` whose `collaboration` member is a scoped `CollaborationObservation`: `scope` (repository/project/plan/milestone/query key, including page bounds for a page), `completeness` (`complete` | `partial` | `unavailable`), `asOf` and, when a generation was observed, the authority stamp plus collaboration and catalog revisions. `asOf` is when the local snapshot was established — never file mtime, provider freshness, or a cross-file lock; `unavailable` carries `asOf: null` and `authority: null` with a code. `storeRevision`/`catalogRevision` in the envelope refer only to collaboration and are `null` when not observed.

Source requirements are declared per view, and a required source that cannot be read refuses rather than answering placeholder data:

- `issues`, `issue-detail`, `projects`, `roadmap` and `issue-flow` require collaboration only.
- `workflows` and `workflow-detail` require execution and disclose an optional catalog association; a project filter makes that association required.
- `iterations` and `iteration-detail` require execution and collaboration.
- `overview` requires both of its combined counts.
- Execution-only status and authority probes never open collaboration.

Resolving the selection is part of admitting the source, so a selector outage or an unopenable cache is an unavailable SOURCE under the same required/optional rule: an optional association degrades to an `unavailable` observation (preserving the checked `source`, `selectorCommit` and `generation` when they were resolved) while the view's execution data is served, and a required one refuses. No local fallback is opened in its place.

A known content gap is reported as `partial` with its original code. Findings evidence (`status findings-cleanup`, plan completion) must be one complete scoped observation of local open issues through `provenance(kind=plan, origin=scoped, target=<plan>)`; missing scope is `collaboration.observation-incomplete`, and a preflight observation that no longer applies is `collaboration.observation-stale`. Milestone delivery checks zero open issues inside its own collaboration mutation. Host authority gates probe this lane independently of execution through `probeCollaborationAuthority`: `active` retires the register file route, while `staged`, `absent` and `unavailable` never authorize a raw register write and are never inferred from the execution lane.

#### Remote selection

With `mode=remote`, the same `ReadEnvelope` is answered from the generation's admitted `remote_observations`; no local-authority handle is opened. The observation additionally carries `source: "remote"`, the checked `selectorCommit` and `generation`, and one `providerScopes` entry per selected project (`scope`, `completeness`, `asOf`, `revision`). Its aggregate `asOf` is the OLDEST contributing observation and its `authority` stamp is the private cache identity, never the provider.

- A required view refuses a selected project that is missing, `partial`, `unavailable` or whose access check is no longer current: `remote.unavailable`, `collaboration.observation-incomplete` or `collaboration.observation-stale`. It never answers zero rows or a zero aggregate from an unobserved project, and a repository count needs every selected project.
- Freshness has two clocks, and both must hold: the latest positive access check must be current, and the observation's `asOf` (the provider traversal's start) must be inside the same 60-second window. A current check over an older traversal is `collaboration.observation-stale` for every required view, count, rollup and gate, while an optional view discloses the same code as unavailable instead of a complete stamp.
- A narrowed query declares exactly the projects it contributes and the cache loads only those projects' snapshots. Another selected project's missing, partial, expired or unparseable evidence neither refuses nor contributes to it; an unfiltered or repository-wide read declares every selected project. `overview` declares its project for the whole response, including the `workflows` member's catalog join (that member's execution rows remain the global summary).
- Issue views read MStar subjects only for `items`/`total`/`projectCount`, disposition/severity/findings counts and the rollup. An unmarked provider issue is visible as `kind:"provider-only", issueRef:null` (its native title and status are display fields) and is never counted, given a disposition, closed or adopted. `issue show --id <IssueRef>` resolves the stable reference; a native record needs its exact provider UUID plus `--project <local-project-id>`, and a display id or a guessed project refuses `issue.scope-refused`.
- `project`, `roadmap` and `milestone` reads answer the snapshot's portable identity, roadmap Markdown (parsed) and milestone grouping; the catalog's registered rows carry checkout-relative locations a snapshot does not have, so `catalog list|show` refuses `remote.unavailable` and the dashboard identity views are the supported remote catalog read.
- Findings and plan completion use the same complete-scope rule over the remote MStar subjects, and the witness identity is the exact selector: the pre-commit re-sample compares `selectorCommit` and `generation` as well as the private cache stamp and aggregate revision, because a successor generation restarts its per-generation revision counters. A partial or stale scope refuses instead of reading as "no findings".
- Every cache mutation re-proves the checked selection on the live ref immediately before commit (and, for a remote cache, the private store id/epoch on the locked connection). A selector that moved to a `draining` or successor generation while the writer waited rolls the effect back with `collaboration.stale-binding`. Git and SQLite are not claimed to be atomic; only the stale window this process can observe is refused.
- `remote adopt-issue --project <id> --issue <provider-issue-id> --operation <uuid> --input <file|->` validates the strict adoption document against the exact observed unmarked native issue and freezes ONE durable `issue-adopt` intent. An already marked issue, or a reference already bound to another provider issue, refuses `remote.scope-mismatch`; a caller-supplied title or project is not part of the document, and no cache-only adoption exists. The verb's exit 0 discloses the intent (`state: "enqueued"`), never an adopted issue.

#### Remote write outbox and recovery

Every remote write is a durable intent in `remote_outbox`, frozen before it is reported: one caller-owned operation UUID, the provider binding it was prepared under, a canonical request hash, and the normalized `RemoteEvent`. The effect and its evidence are separate rows (`remote_outbox_receipts`), and only a validated receipt is effect success. States are `enqueued`, `unconfirmed`, `confirmed`, `conflict` and `abandoned`; the only transitions are `enqueued → unconfirmed → confirmed|conflict`, `unconfirmed → unconfirmed` for inconclusive evidence, and `enqueued → abandoned` or `unconfirmed → abandoned` after a recorded pre-send `not-sent`. There is no elapsed-time takeover, no retry verb and no reuse of a dispatched operation id. A write the observed authority already carries is answered by its own business no-op instead: the same operation id records a SETTLED claim holding that write's replay identity, request hash and answer, never the observed subject as a new provider event — an observation may legitimately carry history the replacement contract refuses, and the claim stays readable, non-dispatchable (no attempt, no receipt) and identical-replay-only.

| Command (`mstar store collaboration remote …`) | Effect and answer |
| --- | --- |
| `outbox-pending --harness <abs> --project <id>` | The current binding's `enqueued` intents only, FIFO by `(createdAt, operationId)`, as summaries without a send permit. |
| `outbox-show --harness <abs> --operation <uuid>` | One intent's binding, state, attempt id, request hash and frozen request — or, for a settled no-change claim, its recorded replay identity and answer (`event: null`) — so a host can look up an uncertain attempt after a restart. Never a permit; content is withheld (`disclosure: "metadata"`) while the project's verified access check is not current. An unknown id refuses `remote.intent-not-found`. |
| `outbox-dispatch --harness <abs> --operation <uuid> [--input <file\|->]` | Issues the ONE send permit for the oldest enqueue of its binding and marks it `unconfirmed` in one committed transaction, before any provider call. A replay returns state only. A reviewed resolution additionally requires the host `ForkObservation` through `--input`. |
| `outbox-receipt --harness <abs> --input <file\|->` | Records what one dispatched attempt observed: `confirmed`, `unconfirmed`, `conflict` or `not-sent`. Exit 0 acknowledges the durable evidence; only the returned `state: "confirmed"` is an effect success. |
| `outbox-reconcile --harness <abs> --input <file\|->` | Records read-only recovery under the intent's ORIGINAL binding, including a draining previous generation. It never issues a permit and never authorizes a provider call; `not-sent` is refused because a lookup cannot prove nothing was sent. |
| `outbox-resolve --harness <abs> --operation <conflicted-uuid> --input <file\|->` | Freezes a reviewed replacement under a NEW operation id, same target and binding, with the freshly observed complete fork heads as parents. One resolution per fork; the original event and its conflict proof are retained and never rewritten. |
| `outbox-abandon --harness <abs> --operation <uuid> --reason <text>` | Explicit abandonment before dispatch, or after a recorded pre-send `not-sent`. The reason and the attempt history are retained; an ambiguous effect is never abandoned as absent. |

Ordinary business verbs in a `remote` checkout (issue capture/occurrence/triage/close/reopen/link/milestone assignment, milestone writes, roadmap replace/import, catalog register/update/link) freeze their normalized event through the same lane and refuse `remote.effect-pending` with `{operationId, state, confirmedComponents}` plus the outbox route; a composite reserves its execution intent first and reports `collaboration.operation-partial` while the provider half is not confirmed. Replaying the identical business verb under the same operation id returns its recorded result once the intent is `confirmed`, and finalizes only the outstanding execution delta for a composite. `issue-sync` keeps its mirror-only inputs and refuses a remote checkout; a project move and a pinned-plan registration refuse by name because they are not admitted remote rewrites.

Exit codes stay the contract's: a malformed or unreadable `--input` document is usage (exit 2) and mutates nothing, a domain refusal is exit 1, and a successful inspection or durable state recording is exit 0 with the actual state. No command opens a provider connection.

#### Sandbox handoff and durability

A fresh sandbox recovers a confirmed collaboration picture from exactly two durable sources: the provider's confirmed records and pushed Git. Its bootstrap is the ordinary sequence — clone the tracked branch, `remote status`, verified `remote bind`, `store init` for a fresh execution lane, then a complete `observe` — and it reads neither the first sandbox's `HOME`, workspace, cache nor execution store. Nothing is flushed at the end of a session: the effect exists once the provider receipt is `confirmed`, and the tracked result exists once Git carries it, so a sandbox removed after those two facts hands off everything a successor needs.

Durability is exactly the survival of those two copies. The host handoff reports `remote.handoff-unavailable` — a host report, not a CLI exit — naming the `missing` and `recovered` components from `provider`/`git` and `recoverable: boolean|null`: `true` when a missing component's surviving copy is proven, `false` when its copies are proven gone, and `null` when its survival is neither proven nor disproven. A component survives only as itself, and the Git component is handed off only by the tracked branch a fresh clone reads: a visible native issue without its MStar marker is not the confirmed record, a Git result another ref still reaches is not that handoff (it stays `missing` while `recoverable` is `true`), and an object no ref reaches is not the pushed result and proves no surviving copy. Losing one source is reported by name while the other stays usable, though neither copy replaces the other; losing both is irrecoverable, and no command reconstructs the missing data. A request found only after a lost response is confirmed by unique exact evidence before it can be handed off, never by a guessed create or a reported success.

Implementation status: the handoff is proven locally against the controlled host fixture (two sandboxes with separate `HOME`/workspace, a local bare Git origin and in-process provider state that renders its own confirmed records into later traversals), and the private cache is a rebuildable observation, never a backup. Live Linear permissions, field-fidelity limits, exact event round-trip, Git server protection policy and operational sender exclusion remain unverified until separately authorized release/operational acceptance.

### Cross-domain operations and their receipts

Four composite actions span both domains — residual add, residual close, execution registration, and minimal import (including its upgrade caller). Each keeps a durable intent in the execution store's `execution_collaboration_intents` (`prepared`, `declined` with its deterministic cause, or `confirmed`) and its effect plus receipt in the collaboration lane's `collaboration_operations`; a standalone collaboration write is one-domain. The execution delta and the collaboration effect commit in separate `BEGIN IMMEDIATE` transactions with no nested write transaction and no `ATTACH`; each reservation excludes only the facts its operation will finalize.

An accepted operation whose work is outstanding refuses `collaboration.operation-partial` with the operation id, its phase (`prepared` or `collaboration-confirmed`) and the confirmed components; it is never success and the same id resumes it. A committed effect whose acknowledgement never landed keeps the business result and discloses `collaboration.acknowledgement-pending`: replaying the same operation repairs only the acknowledgement, while a missing or unreadable effect row is not repairable by replay and must be reconciled under the admitted authority.

### Mirror delivery and replay

Mirror delivery is split by design: the engine records run leases and results (`sync_runs`, `sync_cursor`, `issue_sync_state`) in the collaboration database; the host performs the Linear calls. `mstar issue-sync pending --project <id>` returns the `runId` it holds; `mstar issue-sync apply --project <id> --results <file|-> --run <runId>` continues exactly that run; results that name no run are refused (`sync.run-held`) and are reconciled with `mstar issue-sync ingest --project <id> --records <file|->` or named with `--adopt <localId>=<issueUrl|externalId>`. `--take-run` replaces a holder the operator confirmed dead and records no results. No credential, provider transport, or provider retry exists in the CLI or engine, and importing remote observations stays ledger-only and one-way.

### Backup and restore

`mstar store backup --out <abs-manifest>` publishes a **verified pair**, never one image sold as a backup: an execution image and a collaboration image are copied with their own SQLite snapshots into private, uniquely owned files beside the manifest, each re-opened and verified against its own bytes and row counts. Each domain must then hold still across its own snapshot window and match its own image: the execution generation (store id, epoch, revision, catalog revision) is compared before and after the copy, and the collaboration generation (its own store id, epoch, revision, catalog revision) is compared against both the live re-read and the verified image. The two are **separate generations**: the receipt records distinct execution and collaboration store ids, epochs and revisions, and never requires them to be equal. On top of that per-domain stability the pair needs a causal boundary — the execution root holds no prepared composite (live or in the frozen image), the lane is ACTIVE with no pending cutover claim and no unacknowledged or unreadable composite effect (a recorded decline is settled history), and no composite effect naming the paired execution store comes from an execution epoch ahead of the paired image. The two images are linked into their canonical names and the manifest published, all create-only. Every failure is `collaboration.backup-incomplete`; an image without a manifest is an interrupted attempt, not a backup. A repository backup covers this checkout's execution store plus the repository's collaboration image; it promises nothing about other clones' execution stores.

`mstar store collaboration restore --harness <abs> --backup <abs-manifest> --operator <name> --attestation <abs>` treats the operator-supplied manifest as the pair's authority: the supplied receipt must equal it, each image must still describe its own recorded generation (execution store id, epoch, schema, revisions and counts; collaboration store id, epoch, state, revisions and counts), the same causal and quiescence boundary must hold, and the addressed checkout must be able to own the authority. It then stages a private copy, bumps the restored collaboration epoch, records the restore receipt in the same transaction, and publishes create-only. An absent target is the only admitted destination: a live, corrupt or foreign collaboration authority is never overwritten, quarantined or deleted, and execution sessions, leases and rows are neither copied nor changed. Execution disaster recovery keeps its own explicit route — `mstar store execution export`, `restore-preview` and `restore` — which never writes, replaces or quarantines collaboration. There is no claim of atomic restoration across the two files; a single-domain restore leaves the other domain exactly as it was.

## Invariants

- **One collaboration database per canonical repository per user.** Clones and worktrees of one origin resolve the same database; forks, other repositories, and origin-less repositories without an explicit id do not.
- **Identity is the origin (or an explicit id).** Checkout paths, Git authors, branches, and provider markers never select authority.
- **Mode is explicit and single.** `local` and `mirror` share one local authority; `remote` selects only the verified provider projects, and no unavailable mode selects a local fallback or a second writable copy.
- **Staged is not active.** Only an activation (fresh bootstrap, cutover, or restore) publishes a generation; staged bytes are never runtime business data.
- **A bound checkout is never retargeted.** A different resolved key/mode, store id or epoch refuses `collaboration.stale-binding` instead of drifting onto another repository's data.
- **Missing or partial evidence is a named refusal.** No consumer turns an unavailable, incomplete or stale collaboration source into zero, an empty list, or a successful gate.
- **Evidence carries its scope and time.** Every observation names what was observed, its completeness, and `asOf`; it never claims a provider lock or an atomic cross-domain predicate.
- **Two domains, separate receipts.** A composite operation's intent, effect and acknowledgement live in their owning domain, and a partial outcome is never reported as success.
- **Backup is a verified pair; restore is create-only.** Each domain is checked against its own before/after generation and its own image — the pair records distinct execution and collaboration store ids, epochs and revisions — and a restore never overwrites an existing authority.
- **Provider I/O stays in the host.** The CLI and engine hold no Linear credentials, transport, or client, so every provider read and write is the host's own call. The supported remote lane is host-mediated and implemented: in five steps the host selects and binds the verified scope, observes the bound scope, adopts one exact unmarked provider issue, dispatches exactly one queued intent, and records or reconciles the provider's answer — each step a `remote` verb below acting only on the normalized document the host supplies. A complete round trip, the adoption, the lost-response settlement (a unique exact lookup confirms, while absent or ambiguous evidence stays unconfirmed), conflict detection with the competing provider record preserved and the cache invalidated, and a stale-base refusal that writes nothing are proven against the controlled host fixture; the suite executes no fork resolution or abandonment, so those verbs stay specified rather than proven. Live Linear behaviour stays unverified.

## Change obligations

- **A collaboration schema change** (table, column, migration) → update the table inventory, the admission rules, and [store-authority.md](store-authority.md) when the execution-side pin or fence ledger changes.
- **A new or renamed refusal code** → add it to the code list with its trigger and supported recovery, and update the shared command recovery text.
- **A change to identity, mode, path composition or binding** → update identity/location, the mode table and the Breaking changelog fragment; a behavior change also updates the operator commands here.
- **A new consumer or a changed source requirement** → update read completeness and the view declarations in `store-read.ts` in the same change.
- **A change to the cutover, fence or lock protocol** → update the cutover section and [store-authority.md](store-authority.md) (fence ledger, execution schema advance).
- **A change to the backup pair, restore boundary, or composite receipts** → update that section and the command list.
- **Provider work, a new remote capability, or cross-authority moves** → an ADR first; this page states only implemented, locally verified behavior. The outbox and the host lane are the provider-free surface: the CLI opens no provider connection, and provider transport remains unimplemented. A change to a remote verb, or to a host-lane step, refusal or recovery, updates this page and `skills/mstar-remote-collaboration/` together. The lane's round trip, adoption, lost-response settlement, conflict detection and stale-base refusal — like the sandbox handoff and provider isolation — are proven only against the controlled host fixture; live Linear permissions, field-fidelity limits and exact event round-trip stay unverified until separately authorized release acceptance.
