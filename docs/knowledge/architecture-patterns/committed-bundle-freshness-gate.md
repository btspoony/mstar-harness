# Committed bundles for checkout-root plugins

## Problem

Hosts whose plugin root IS the repo checkout (zcode, and by convention cursor/codex/kimi in this repo) have no plugin build step: a config referencing a build output that lives only in a gitignored tree resolves to a nonexistent file after install. Conversely, tracking build outputs invites the question of how a stale copy is noticed — and the answer must not be a byte comparison, which measures the bundler version that produced the artifact rather than the source it was built from. (The original instance was `packages/mcp/dist/plugins/<target>/`; `packages/mcp` and its per-host bundles were deleted in favor of the `mstar mcp` CLI subcommand — `29c97f16` — so `mcp/bundles/` and `mcp:build` no longer exist. The pattern and its lessons below survive on the `hooks/` artifact and on the generated dashboard assets.)

## Decision

Commit generated bundles into the plugin-root-visible path, mark them `@generated`, and have CI **build** them as a blocking step. The live instances in this repo: `hooks/*.mjs` (engine inlined by `scripts/build-zcode-hooks.ts`; CI step `ZCode hooks bundle build` runs `bun run engine:build && bun run hooks:build`, `.github/workflows/ci.yml`) and `packages/commands/src/dashboard/assets.generated.ts` (regenerated by the blocking `Typecheck` step and again by the CLI build used for packaging). Configs reference the committed path via the host's documented plugin-root variable. A package-internal build tree stays gitignored. The committed bytes are deliberately **not** compared: the byte form depends on the exact bun/bundler version (1.4.0 and 1.4.4 emit different text for identical sources), so a diff reports the build environment rather than the change, and a recorded source/output digest pair is no better (`tooling-decisions/generated-artifact-engine-resolution-identity.md`). The artifact is proved by the suites that execute it; the committed copy is re-taken by `release:prepare`.

## Process lessons (same iteration)

1. **Registry union regressions recurred three times** (C6b dropped pr-review, C6c dropped process, C6d dropped judgment) because per-task scoped proofs never exercised the composition. Fix: every family round's proof must include the registry/definitions test (whole-directory preferred), not just its own file.
2. **Smoke must not self-substitute host variables**: the first packaging smoke expanded `${ZCODE_PLUGIN_ROOT}` itself against a synthetic root, hiding the missing-bundle failure. Assemble the layout the manifest declares, assert the resolved executable exists, then launch.
3. **Environment isolation claims need implementation receipts**: "PATH excludes mstar" was asserted before the smoke actually constructed a sanitized PATH (temp bin dir with only node/bun symlinks + a pre-spawn `mstar` non-resolution assertion).

## Rebuild order

The committed copy is a release artifact, not something a source change re-takes: `release:prepare` rebuilds it. When a local rebuild is needed (to exercise the built hook, or to check a source change against real output):

1. **Rebuild the inlined dependency first.** `scripts/build-zcode-hooks.ts` transpiles only the hook; it inlines the gitignored `packages/engine/dist/engine.js`. A hooks-only rebuild inherits whatever engine the last local build left there, so rebuild `engine` and then `hooks`.
2. **Execute the result.** The hooks behaviour tests run against the built bundle; that execution is the evidence. Never add a checked-in digest, and never diff build output against the committed copy — both describe the machine that produced the bytes, not the source they came from.
