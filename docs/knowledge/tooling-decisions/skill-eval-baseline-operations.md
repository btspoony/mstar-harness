# Skill-eval baseline operations: frozen manifests, resume, known failure classes, honesty limits

## Context

iter-20260907 delivered a reproducible skill evaluation baseline (`scripts/skill-eval/`: manifest/cases/runner/report CLI) plus an adopted evidence corpus. Every future skill-thinning or load-contract decision should run against it instead of ad-hoc judgment. Operational semantics are non-obvious and were paid for across SP1/SP5/SP6 real runs.

## Guidance

- **Prepare → run → report**; `$EVAL_MANIFEST` is the absolute prepared-manifest path generated by `prepare` into the contained fixture root (never HOME/CODEX_HOME). Compare arms only through one frozen manifest pinned to explicit source refs (per-file sha256 closures); changing corpus bytes requires a re-version + provenance note (A1 re-freeze rule), never post-hoc assertion edits.
- **Resume is grade-based and safe**: the scheduler skips only units with a grade; an interrupted in-flight unit re-executes fresh and its stale partial turn dir is auto-quarantined under `aborted/`. A killed session's evidence survives on disk — distill aggregates into the control sdd eval/ dir before any `.tmp` cleanup.
- **Known failure classes are arm-symmetric and pre-existing**: `pm-dev-4` (resume-turn read visibility), `audit-dev-3` (synthetic blocking gate unenforceable by real host sandbox — the requested write lands), `close-dev-4` (genuine isolation escape: writes beyond allowed set in BOTH arms). Adoption gate = critical delta 0 + no normal-success regression (per-case symmetric), NOT zero fails.
- **Two structural honesty limits**: (1) arm divergence is provenance-only — the runner hashes/closures differ per arm but never materializes skill content into workspaces, so behavioral effect of a text change is NOT causally established; load reduction is observed bytes/reads only. A materialization seam is the recorded next-iteration remedy. (2) `codex exec --json` streams carry no model-identity field — fixed-model claims are impossible; `observedModel` stays null+reason.
- **Long runs vs interactive sessions**: dev ≈ 90 min, heldout 3-repeat ≈ 100+ min. Launch with `nohup … & echo $! > pid` and poll (`sleep 45; kill -0 …; tail -3 log`) — synchronous waits have killed subagent sessions repeatedly.
- **Fresh worktrees must `bun install && bun run engine:build` before tests** — otherwise `@mstar-harness/engine` silently resolves to the primary checkout's stale dist.

## Why This Matters

Every adoption decision in iter-20260907 (SP2 load contract, SP5 thinning batches, SP6 router) was gated by this runner. Misreading resume semantics or the failure classes would either fabricate regressions or mask real ones; the materialization limit bounds what ANY run can prove.

## When to Apply

Before adopting skill-text changes; when interpreting eval reports (exit 1 = completed assertion failures, exit 2 = infra/unverified); when planning the next efficacy claim (heldout must run on the frozen digest first).
