## [4.5.1] - 2026-11-11

### Harness

- The three tracked corpora — `{KNOWLEDGE_DIR}`, `{SPECS_DIR}`, `{ADR_DIR}` — now default to `<repoRoot>/.agents/<kind>/`. `packages/engine/src/path.ts` drops the harness-first candidate and the `{HARNESS_DIR}/<kind>/` fallback: the chain is `.mstarc` → `.agents/<kind>` → kind-specific secondaries → a **legacy read-only** `{HARNESS_DIR}/<kind>/` tail, and an absent corpus creates `.agents/<kind>/` (skipped by `create: false`). A tracked corpus therefore survives a fully gitignored `.mstar/`.
- `<repoRoot>` is now an explicit anchor rather than an assumption: `resolveSpecsDir` / `resolveKnowledgeDir` / `resolveAdrDir` accept `opts.repoRoot` (defaulting to the harness dir's parent), and the CLI, `scaffoldHarness` and the catalog pass the checkout they know — so a harness configured outside the repository creates the corpus in the checkout that can commit it, not beside itself.
- `.mstarc` stays the only authority: a declared `knowledge_dir` / `specs_dir` / `adr_dir` is returned as declared, ahead of every candidate. Repositories that declare keys, including this one on `docs/{knowledge,specs,adr}`, keep their layout.
- Writers must **resolve the symbol before writing** — read `.mstarc`, or run `mstar path resolve` — and never compose a default path. That rule is now stated in `mstar-conventions` (symbol-table preamble and resolution chains), `mstar-doc-corpus` § Layout defaults, `mstar-knowledge` § Storage, `mstar-artifacts` § Workflow and `docs/specs/architecture/document-corpus.md`; it is the root fix for issue #714, where two competing defaults let an agent write an unshareable document into the harness root.
- The prose moved but two code paths did not, so they now resolve instead of composing: the `compound` write-gate matches the `{KNOWLEDGE_DIR}` the resolver returns (a literal `{HARNESS_DIR}/knowledge` had silently stopped covering `.agents/knowledge/`), and `compoundRefreshScope` takes the already-resolved knowledge root from its caller. `scaffoldHarness` derives its bootstrap `.mstarc` corpus keys from the directories it creates, so a nested harness (`harness_dir=runtime/harness`) declares `../.agents/<kind>` instead of a second corpus beside itself, and an already-declared corpus key is seeded where it points rather than in a second `.agents/<kind>` tree.
- Recorded as `docs/adr/implemented/architecture/2026-11-11-corpus-default-location.md`.

## [4.5.0] - 2026-11-11

### Harness

- **Acceptance carrier rename:** the completion payload member is now `acceptance: {gate, decision, report}` (was `qa`), the prepare flag is `--acceptance-gate` (was `--qa-gate`), and the emitted evidence label is `acceptance.report`. The gate value stays `pm-acceptance`. Stored completions written as `qa` still validate and read through one read-side acknowledgement; new submissions carrying `qa` are refused with a message naming `acceptance`. The prepared configuration's stored `qa_gate` key is unchanged, and no alias flag exists.
- **Touched surfaces:** the owning skill prose (`mstar-artifacts`, `mstar-roles` PM references, `mstar-use-cli`), the iteration and project-governance references (`mstar-iteration/references/phase-2-worktree-lease.md`, `mstar-project-governance/references/migration-source-shapes.md`), `docs/commands.md` / `docs/runtime-reference.md`, the regenerated ZCode hook bundles (`hooks/session-context.mjs`, `hooks/mstar-write-gate.mjs`, built with the pinned Bun 1.4.0), and a knowledge-corpus cleanup that leaves current practice only — historical `## Source` provenance and `QA gate` labels are gone from the affected pages.
- **Scaffold bootstrap layout:** `mstar harness scaffold` now produces the layout the harness recommends. The canonical `.mstar` snippet ignores the process root as a whole and no longer lists `.mstarc`, so process artifacts stay local while the layout declaration travels with the repository. `scaffoldHarness` writes a tracked `.mstarc` at the harness dir's parent when no declaration is in scope and that parent lies inside the scaffold root (`harness_dir` plus `knowledge_dir` / `specs_dir` / `adr_dir` = `.agents/*`), creates `plans/` `iterations/` `sdd/` `reviews/` `projects/_default/` under the harness dir, creates the resolver-returned `.agents/knowledge|specs|adr` corpora instead of hardcoded `.mstar/knowledge` and `.mstar/specs`, and seeds the ADR tree with `README.md`, both templates and the four bucket directories (class directories are created by the first record). `harness.scaffold` writes the harness rule file at `.agents/AGENTS.md`, the only location tracked in both layouts. Reruns create and rewrite nothing, and an existing author-owned `.gitignore` or `.mstarc` is never touched.
- Updated `mstar-conventions` (path symbols, initialization steps, git-tracking contract, bootstrap layering), `mstar-roles/references/project-manager/plan-management.md` and the new ADR `docs/adr/implemented/architecture/2026-11-11-scaffold-result-layout.md`.
- **The issue store gains an honest terminal state for a removed subject: `obsolete`.** One authoritative tuple in `packages/engine/src/issue.ts` now defines the disposition vocabulary, and every server schema, filter, aggregate, history query and outbound mapping derives from it instead of repeating a list. An `obsolete` close requires a nonblank reason and at least one removal reference, refuses any `canonicalIssueId` (including `null`/`""`) before mutation, and refuses with `issue.invalid-disposition` plus the exact removal-evidence recovery. Migration 19 is append-only and preserves existing rows, relations and triggers; the browser projection is generated from the same tuple, and `obsolete` maps to `Canceled` on outbound Linear pushes.
- **The external half of the dashboard is removed.** The `sync-binding` screen, its `#sync-binding` route and navigation entry, the `/api/sync-binding` read, the `querySyncBinding` engine view, the shell-chrome nav key and both locales' copy are gone end to end; a stale `#sync-binding` address now lands on the overview and a stale `/api/sync-binding` request answers the dashboard's structured `not-found`. The dashboard renders the local `store.db` only — the issues/detail, issue-flow, workflows/detail, iterations/detail, roadmap, projects and overview reads keep answering.

## [4.4.0] - 2026-11-09

### Harness

- **Delivery evidence no longer carries a hand-recorded PR identity.** The `delivery.pr` member is gone: the PR head and target ARE the registered `branch.work` / `branch.target` anchors (contract §4d), so recording a copy is refused as an unused member and a repaired anchor can no longer strand a frozen identity.
- **`delivery.merge` is now one optional fact: the provider commit.** The shape is `{ commit?: string }` — a full lowercase 40- or 64-hex commit id. The free-text `provider` / `evidence` attestation, which gated `completed` while nothing verified it, is deleted.
- **The merge is proven from local Git, once, for both consumers.** `verifyDeliveryEvidence` runs the pure evidence rules plus an association proof in the plan row's recorded `metadata.worktree_path` (the first recorded checkout that resolves the target ref, so a path repointed at another clone cannot decide it): the target ref is read remote-first (`refs/remotes/origin/<target>`, else `refs/heads/<target>`) because a provider merge lands in the remote and `git fetch` advances it while a local head may stay stale; an ancestor `branch.work` tip passes; otherwise every delivery commit patch-equivalent upstream (`git cherry <target> <tip>` non-empty, every line `-`) passes with no recorded value, but only for a merge-free delivery history (`<target>..<tip>` holds no merge commit, which `git cherry` never reports); otherwise a recorded `merge.commit` passes only when it exists as a commit, is contained in the target, AND carries the delivery's own diff (equal `git patch-id --stable` for `<commit>^..<commit>` and `fork..tip`). Reachability alone is not proof. Close and the read-only Phase-6 gate call the same function, so they cannot disagree; an unproven merge is `PHASE6_DELIVERY_MERGE_UNPROVEN` on both.
- **Stored blocks stay readable.** Snapshots recorded by the previous shape keep their `delivery.pr` and free-text `merge` as history: persisted-state validation reads those members as absent instead of invalidating the snapshot (the same read tolerance the pre-rename `branch.source` spelling gets). Every write path still refuses them.
- **Refusals name the cause and an executable recovery.** An unproven merge says which relation failed — no delivery ref, a tip outside the target, commits with no patch-equivalent counterpart, an absent recorded commit, or a recorded commit whose patch id differs from the delivery diff — and points at fetching the target branch, restoring the delivery branch ref, retrying, or recording the provider merge/squash commit via `mstar workflow evidence`. No network or provider call is added; every Git read uses the existing argv-array helpers.
- **Known limits, documented rather than hidden:** a rebase or single-commit squash proves itself through `git cherry`; a multi-commit squash is not provable from patch equivalence alone (each commit's patch id differs from the squashed patch) and needs its provider commit recorded; a squash that resolved conflicts differently has no local proof, so its terminal state is `mstar workflow lifecycle --status stopped|failed --reason`; a target with no local and no fetched ref is a refusal, never a pass (a stale local head alone is not, because the remote ref is read first). The proof belongs to the close, once: the read-only Phase-6 gate reads the stored terminal facts and never re-litigates a merge whose checkout routine cleanup already removed, so a completed lifecycle keeps passing after `worktree cleanup --apply`.
- `mstar workflow evidence` publishes the new shape (`merge { commit? }` — the member optional, but a supplied block must carry `commit`, which the CLI schema now also requires; no `pr`) and its help text; the deleted anchor/PR advisory warning and its close-time immutability refusal are gone with the duplicate identity.
- Updated `mstar-artifacts/references/plan-workflow-lifecycle-contract.md` (§3 stage table, §4d/§4f/§4g), `mstar-iteration/references/phase-6-post-merge-close.md`, `mstar-artifacts/references/status-and-residuals.md`, and `mstar-artifacts/templates/plan.main.md`.
- **The report-only fulfilment gate is gone.** `verification/report-only` no longer requires a recorded `delivery.completion` block before `plan complete` or the terminal close. The `completion` member is deleted from `WorkflowDeliveryEvidence`, the structural validator and the `mstar workflow evidence` payload; recording it is refused as an unused member.
- **`completion_policy` stays a registration-time declaration.** The registered policy declares what the deliverable is; it is not a runtime artifact to fulfil with a sentence nothing verifies. `verifyDeliveryEvidence` returns the pure consultation result for this route — no Git proof, no fulfilment lookup.
- **What `completed` means on this route is now explicit:** every row `Done` plus QC/QA. Report-only `completed` no longer claims a recorded self-attestation, and real-environment or external-artifact proof is outside this route rather than mimed by a string.
- **Stored blocks stay readable.** A snapshot recorded under the previous shape keeps its `delivery.completion` as history: persisted-state validation drops it (the same read tolerance `delivery.pr` and the free-text `merge` get) while every write path refuses it.
- Updated `mstar-artifacts/references/plan-workflow-lifecycle-contract.md` (§1, §3 route table, §4g, §7, binding negatives), `mstar-roles/references/project-manager/plan-management.md`, `mstar-iteration/references/phase-6-post-merge-close.md`, and `mstar-use-cli/references/plan-and-workflow.md`.
- **Harness roots resolve from the main worktree only.** `resolveHarnessDir` no longer adopts a linked worktree's tracked `.mstarc` copy: a start path whose Git checkout differs from the main worktree resolves through the main root, so a worktree can never look like a process root. Subdirectories of the main checkout keep their existing upward rungs, and `opts.localProbe` keeps the local probe for callers that ask about the caller checkout itself.
- **Tracked results follow the caller's checkout.** `resolveTrackedResultDir` (used by `mstar path resolve`, `mstar path check` and the catalog) computes the target as the main checkout sees it, then applies that repo-relative path to the caller's checkout when Git does not ignore it there. Gitignored targets, targets inside the harness dir, and another repository's checkout stay on the main one. `StoreContext` gained an optional `checkoutRoot` for catalog roots.
- **One bounded Git-probe implementation.** The path resolver, `path check`, the worktree checks and the host write gates now share `engine/src/git-probe.ts` instead of three divergent copies: `mainWorktreeRoot` parses `git worktree list --porcelain -z` (so a C-quoted path never yields a bogus root), `checkoutRoot` is the single `rev-parse --show-toplevel` probe, and `gitIgnored` keeps its explicit "Git could not answer" state. Every probe is bounded by `MSTAR_GIT_PROBE_TIMEOUT_MS`.
- **Probe failure is fail-closed.** `resolveHarnessDir` runs the main/checkout probes only where they can change the answer (`localProbe`/`workspaceRoot` short-circuit), and when the caller's checkout is known but the main root is unreadable it answers no harness root instead of silently adopting the worktree's own.
- **The catalog `repository` root follows the caller's checkout.** A linked-worktree invocation resolves `repository` in its own checkout (same repository only); `harness`, `plans` and `iterations` stay on the control checkout, so one catalog operation answers from one checkout.
- **Deleted `mstar sdd evidence capture|verify`.** No gate consumed the retained bundle: the record schema, input digests, tool fingerprints and reuse assessment are gone, together with the CLI capture runner and its MCP effects.
- Retaining a check's output is now a plain redirect to a file under `{SDD_DIR}/evidence/` with the path cited in the report; reviewers read the raw log and never re-run the command.
- The remaining `mstar sdd` verbs (`workspace`, `task-brief`, `review-package`, `check-context`) are unchanged.
- **PR review admits defects, not polish.** Findings must identify an observable wrong outcome introduced or worsened by the change, with one narrow exception for diff-introduced, exemplar-cited, behavior-neutral convention `nit`s; test/document wrong-artifact restrictions still apply. Missing or weak tests, coverage requests, documentation polish, naming, formatting or abstraction preferences, and execution-dependent claims are excluded. Synthesis applies admissibility before evidence verification for `may-fix` and `nit`.
- **Removed the `unverified` result channel from the engine, commands family and CLI.** The `--unverified` flag, report key, tally bucket, score deduction and display row are gone. Runtime proof belongs to CI, QA and explicitly requested E2E; the review no longer retains or scores claims that need execution to settle.

## [4.2.3] - 2026-11-06

### Harness

- **A running workflow's operation receipts are no longer count-capped.** `execution.receipt-retention-exhausted` and the exported `RUNNING_WORKFLOW_OPERATION_RECEIPT_LIMIT` constant are gone, with no compatibility shim: a RUNNING workflow refused its next ordinary plan or workflow operation once it retained 256 receipts, and the only recovery it named was to close or adopt the workflow and start a new one — a route an unfinished lifecycle cannot take without discarding the work it still holds. Every receipt the current epoch can replay is a replay anchor, so the engine never evicts one to make room. Retention is therefore logical and lifecycle-scoped rather than numeric: each committed operation of the active lifecycle keeps one receipt row — its persisted replay metadata plus the recorded result payload where the writer stored one, while slim receipts persist the replay address and reconstruct the live state under the same epoch instead of recording a full result. That set grows with the operation count and the payloads actually stored until the workflow terminates, at which point the terminal mutation prunes it to exactly its own receipt. No supported in-place epoch advance bounds a running lifecycle's receipts: restore deliberately preserves prior-epoch receipt rows as history, outside the current epoch's replay scope, and the epoch delete in the create-only initializer can never remove receipts because that transaction refuses a non-empty execution domain. The terminal prune is a SQL `DELETE` that bounds what the store serves; it promises neither constant space nor a smaller SQLite file on disk. Exact replay, changed-intent conflicts, CAS, authorization and normal terminal behavior are unchanged.

## [4.2.1] - 2026-11-04

### Harness

- **PR review gains a fourth merge class, `may-fix`, with a surface gate.** Test and documentation findings are capped at `may-fix` however serious the underlying gap reads — a review contract rather than a lint rule: lint only checks class presence, enum membership and placement, and the merge-class assignment itself stays a seat/PM judgement. `may-fix` is counted, listed in full, captured as an issue and deducted from the score, but it never selects a verdict — a review whose only findings are tests or docs still returns `ship it`. A leftover unmet acceptance criterion obeys the same cap: a test or docs AC increments `may-fix` and can never select `needs fixes` or `blocked`, while an implementation AC keeps the unsafe/safe split. Implementation findings keep the previous bands above the small-impact tier (`critical` → `must-fix`; `high` / `medium` → `should-fix`), while `low` moves from `nit` to `may-fix`. The locked deduction schedule gains `may-fix` `max(6 − 2·(n−1), 1)` → 6,4,2,1,1… with a class cap of 15. The chat header and report tally gain the `may-fix` count; a report or envelope written before the class existed stays valid and reads `may-fix` as 0.

## [4.2.0] - 2026-11-04

### Harness

- **One-way push to Linear.** `mstar issue-sync push --project <id>` sends this project's local issues to the
  bound Linear team: create when no remote identity is known, update the confirmed id when a field changed,
  skip with zero write calls when the normalized payload hash is unchanged. Migration 17 adds the ledger's two
  nullable push facts, `last_request_hash` (the skip rule) and `last_kind_label` (the labels mstar may have
  written, kept as a candidate set because an unconfirmed update leaves more than one possible); the import
  direction leaves both null. Only a confirmed receipt or an explicit `--adopt` ever records an
  `external_id`, so a hash is never treated as proof the remote issue exists.
- **An unconfirmed write can never duplicate a create.** The write adapter classifies every outcome as
  `confirmed` / `refused` / `ambiguous`; `refused` is provably not delivered and records `failed` for a safe
  retry, while `ambiguous` leaves the row `pending` with no id. A 4xx is `refused` only where the server cannot
  have executed the write: `408 Request Timeout` and `425 Too Early` are `ambiguous`, because a deadline or an
  early-data refusal can arrive after the mutation ran. The next run reconciles such rows by the
  application-owned correlation marker `<!-- mstar-sync: <workspace>/<team>/<storeId>/<localId> -->`: exactly
  one match adopts that id, zero or several report `unresolved` and write nothing, and a run with no ambiguous
  residue issues zero listing calls. Title+description equality is never adoption evidence, and the marker
  carries the store's own identity so two harnesses mirroring one team never adopt each other's rows.
  No flag can assert that a remote issue is absent: neither an unresolved create attempt nor any earlier request
  can be proven not to have landed, so while a `pending` row carries no id nothing creates. The three recoveries
  are re-run push so reconcile adopts by marker, record an identity you can see with `--adopt`, or, when the scan
  proves nothing carries the marker and the issue is genuinely gone, `--release <localId>`. A release drops that
  `pending` create to the retryable `failed` edge with the operator's judgement as its reason, so the same run may
  create; a scan that found a match refuses it, because that item's recovery is adoption. The create still takes
  a send-right claim — binding, item and content hash — as its intent record, but the claim is no longer an
  arbiter between runs and no longer carries the ledger revision: the run lease below is what separates RUNNING
  attempts, and a stable per-residue key means a re-run can never mint a new one mid-attempt.
- **One push run per binding, with an explicit takeover.** `mstar issue-sync push` is an operator command, not a
  concurrent service, so it now serialises instead of pretending to be concurrency-safe. Migration 18 adds
  `sync_runs`, one row per `(binding, direction)`; the run is claimed before any candidate work by a single
  insert that fails when a row exists, and released in a `finally` on every exit — completion, refusal and throw.
  A second run is refused with `sync.run-held`, naming the current holder's start time, pid and host so an operator
  can judge whether it is alive, plus both exits: wait for it to finish, or `--take-run` to take it over after
  confirming the holder is dead. `--take-run` REPLACES the row (it never coexists with it), records the takeover as
  the run's reason, and a taken-over run's own release matches nothing because it names its own run token, so it
  cannot free its successor. A scripted parallel push is not supported.
  **What the lease actually arbitrates is acquisition, not the whole run.** The run token is carried into every
  ledger write, so a run that a takeover replaced has its LATER writes refused with `sync.run-taken` instead of
  applied — the successor is unaffected (its own id is the one the row holds) and the ordinary single-run path is
  unchanged. What no guard can do is recall a request the predecessor had ALREADY sent when the takeover landed: it
  may still reach the provider, which is why the reconcile-by-marker scan remains the first recovery and why
  `pending` residue is never created over. Taking the run over from a LIVE holder is therefore unsafe —
  `--take-run` is for a holder the operator confirmed is dead, never a timer or a liveness guess.
  `--release` keeps its meaning; a release still needs no check for a RUNNING create of that residue, but it can
  never see one a dead holder already sent.
- **Labels are resolved, never created.** Kind→label is resolved against the workspace's real label set
  discovered through `list_issue_labels`; a mapped name the workspace lacks refuses that item
  (`linear.label-unresolved`) and other items proceed. A changed kind adds the new label and removes every
  recorded candidate via `removeLabels` — a row with no recorded label only adds, the full-replace `labels`
  argument is never sent, and a host handshake whose schema does not advertise `removeLabels` refuses that
  update before any write. An update whose receipt is unconfirmed keeps BOTH the old and the attempted label as
  candidates, so the retry removes whichever one the remote actually kept.
- **Workflow states are resolved the same way.** Disposition→state is resolved against the bound team's real
  workflow states discovered through `list_issue_statuses`; a mapped name the team lacks refuses that item
  (`linear.state-unresolved`) before the call and names the `[linear.mapping] disposition.<state>` redirect, so a
  renamed workflow is diagnosed in the run instead of failing every item at the provider. The report carries the
  state set the run resolved against, beside the label set.
- **Writes need a write scope.** The run refuses with `linear.scope-insufficient` before any provider call when
  the credential it will actually authenticate with carries neither `issues:create` nor `write`, naming the
  explicit reauthorization (`mstar linear auth login` or the dsh Settings Authorize). Only the effective
  credential is gated: a stored grant that is expired and unrefreshable is not the one used, so an exported
  `LINEAR_API_KEY` supplies the run and decides by its own capability. A refresh never widens a read-only
  grant. Operator recovery beyond automatic reconcile: `--adopt <localId>=<issueUrl|externalId>` records an
  identity you confirmed, and `--release <localId>` clears a `pending` create once reconcile's own scan proves no
  remote issue carries the item's marker. The two verbs are also checked against each other before any write:
  naming one local item under both `--adopt` and `--release`, or under two `--adopt` entries, is refused as
  `sync.operator-conflict` — each entry alone passed its own ledger check, so the adoption used to land before
  reconcile refused the release.
- **Adoption drops the proof of a REPLACED identity.** `--adopt` records the identity you confirmed and, when that
  is a different issue than the row already pointed at, CLEARS the payload hash and label ownership it held: both
  described the previous issue, so carrying them over would report `skipped` for content the newly adopted issue
  never received and let a later kind change remove a label recorded for the previous one. Content therefore
  converges onto the adopted issue in the same run. Re-confirming the id already recorded is not a replacement:
  its hash and ownership still describe that same remote issue, so they are kept and a later kind change removes
  the label it owns. Replacing an identity that is already recorded is refused as `sync.identity-conflict` unless
  `--force-adopt <localId>` names that item.
- **A refused update is visible on the row.** A push whose write the provider refuses reports `failed`; when the
  row already holds an identity, `applied → failed` is not a legal edge, so the cause is recorded through the
  error-only verb instead. The row keeps its state, identity and proof, the dashboard shows the cause, and the
  changed hash still makes the next run retry the write. A `pending` row with no id is untouched as before, so
  reconciliation can still find it.
- **A create lands in the bound project.** `save_issue` is called with the bound `project` as well as the
  `team`, so a created issue sits where the binding says and the marker-based recovery reads (which filter by
  that project) can find it. An update never sends `project`: the recorded identity already lives in the right
  project, and the argument would move it.
- **The state refusal names the key the resolver reads.** `linear.state-unresolved` points at
  `[linear.mapping] disposition.<key>`, where `<key>` is the DEFAULT target state the local disposition maps to
  (`Todo`/`Done`/`Canceled`), because that is the key `stateOfDisposition` looks up. `waived`, `duplicate` and
  `superseded` all collapse onto `Canceled`, and the message says so instead of printing a local disposition
  name no resolver reads.
- **The probe deadline aborts the call it timed out.** `LinearProbeDeps.rpc` now receives an `AbortSignal` that
  fires when the handshake deadline expires, so a transport stuck in flight is cancelled instead of being
  abandoned while it keeps holding its socket. The caller still observes the same single
  `unreachable: Linear MCP handshake timed out after <n>ms` cause; a transport that reports the abort as its own
  error cannot turn that into a transport failure.
- **A refresh commit honours a newer sign-out or grant.** Every writer decides inside `commitLinearCredential`,
  whose lineage check re-reads the file and declines when a `mstar linear logout` or a re-authorization landed
  during the refresh's network round trip — the long window that used to be overwritten. The remaining
  microsecond window between that final read and the rename is accepted: a sign-out landing exactly there can be
  overwritten by the refresh it raced, and the operator clears the stale grant by signing out again. The dsh

- **The store's append-only ledgers are bounded.** A RUNNING workflow now retains at most `RUNNING_WORKFLOW_OPERATION_RECEIPT_LIMIT` (256) operation receipts: the cap is enforced in the same transaction that would insert a new non-terminal receipt, so overflow refuses `execution.receipt-retention-exhausted` and leaves no receipt, revision or effect behind. No replay key is ever evicted to make room — every retained operation id keeps its exact replay and changed-intent conflict behavior — and the refusal names its recovery (adopt or close the workflow under a new operation id, then start a new workflow). A terminal mutation stays exempt and its prune still keeps exactly the close receipt. Coordinator recovery (`recoverExecutionCoordinator`) is the other exempt non-terminal write, and for the same reason: it is the only way back from a stopped holder, so at the bound its receipt is still written and the workflow can then be closed instead of being stranded with no live binding to close it. The `notes.jsonl` ledger compacts at `WORKFLOW_NOTES_LEDGER_MAX_BYTES` (4 MiB) under the store's own `BEGIN IMMEDIATE` write lock, writing a same-directory temporary file, fsyncing, renaming atomically and fsyncing the directory; the newest complete lines that fit the read window are kept, the triggering note always survives whole, and a `workflow-notes-compaction` marker is written as the FINAL row with the dropped byte/line/record counts and the dropped prefix's sha256. Coverage reads a `WORKFLOW_NOTES_LEDGER_READ_BYTES` (1 MiB) tail window, drops the partial first line, and reports `readWindow: {offset, totalBytes, truncated}` plus `compaction` so a truncated read is disclosed instead of being reported as the whole ledger. The rewrite is published only while the ledger still holds the snapshot it classified: a lock-free peer frame that lengthened the leaf makes the compaction discard its temporary file rather than delete that frame, and the ledger is simply retried past the ceiling on the next such append. Every earlier marker is dropped too and counts toward the disclosed dropped bytes, so exactly one marker survives as the final row. That row stays inside the read window until later appends push the ledger past it; coverage then reports a truncated window with `compaction: null` rather than resurfacing the older disclosure. The codex `.bak` growth recorded beside these two surfaces was already bounded to one backup per install; no code change was needed there.
