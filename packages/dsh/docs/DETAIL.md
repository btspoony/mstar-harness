![Architecture of @mstar-harness/dsh inside dsh: a DSH session calling the three native tools mstar_plan_bind, mstar_audit_validate and mstar_execution_clear, the mstar-engine row appended at agent/pre-step, the Morning Star Workflow right-sidebar tab reading /api/mstar/*, and the workspace harness state under {HARNESS_DIR}](preview.svg)

The plugin puts the same workspace harness state behind three surfaces of one DSH session: one model-visible `mstar-engine` catalog row appended to the session's steps at `agent/pre-step` (engine status, iteration phase gate and workspace-state digest, read from `{HARNESS_DIR}`), one panel tab in the right sidebar, and the three native tools the shared MCP connection cannot provide. `mstar_plan_bind` binds the coordinator plan once the engine's workflow/plan addressing, state and concurrency guards pass, and writes this session's `executionBinding` slot in the control root's `store.db`; `mstar_audit_validate` runs the review-report credential scan of `mstar-audit` Hard Rule 4 (`redactSecrets`) under `{REVIEW_DIR}` and reports findings by line and type, never by secret value; `mstar_execution_clear` clears that same slot with no parameters at all, its identity taken from `exec.agent.id`, so it can only reach the caller's own binding and keeps the user's workflow selection and exclusion floor. `mstar_plan_bind` and `mstar_execution_clear` additionally refuse a known leaf seat before any admission or store read. The right-sidebar tab (`mstar-workflow`, "Morning Star Workflow") reads the same state through `/api/mstar/panelSnapshot` and `/api/mstar/dashboardView`, and commits a workflow pick through `/api/mstar/selectWorkflow`.
