# omp host reference

Load when **`mstar-host`** detection resolves **omp** (Oh My Pi / `omp` session, **`task`** tool with **`agent`** / **`tasks[]`** batch shape, **`ask`** tool, **`hub`** tool, or `/skill:pm` / `/iteration-*` from this plugin).

Plan mode: read **`omp-plan-mode-bridge.md`** when `/plan`, plan-yolo, or plan-model / read-only-with-resolve plan UX is active. Parallel PM dispatch: read **`parallel-dispatch.md`** when dispatching **N ≥ 2** concurrent `task` invocations.

## omp-only context

- Plugin markers: **`.omp-plugin/plugin.json`** (Morning Star host marker) and **`.claude-plugin/plugin.json`** (Claude-compatible marketplace discovery). The **npm package** (`@mstar-harness/omp`) ships its own package-root `plugin.json` + `skills/` + `commands/` + `agents/` + `hooks/` + `tools/` mirrors; the **maintainer link path** is `<repo>/packages/omp` (built) — hooks/tools moved into the package, so linking the repo root provides skills/commands/agents only, with NO runtime gates.
- Runtime skills: package `skills/` (or repo `skills/` on the link path) discovered after `omp plugin install` / `omp plugin link` (OMP extension-package sub-discovery) or Claude marketplace install. Plugin commands: `commands/<name>.md` → slash **`/<name>`** — the filename is the command name, with no `morning-star-harness:` prefix (`/iteration-start`, `/iteration-drive`, `/iteration-loop`).
- Plugin agents: **`agents/*.md`** are discovered into the live **`task.agent`** list after install/link + reload. `project-manager` ships **no agent shell here** — the `mode: primary` seat is OpenCode-only (`packages/opencode/agents/`); PM enters via the `pm` skill and is never a `task` dispatch target.
- **No Kimi-style `sessionStart.skill`** — enter PM manually via **`/skill:pm`** (or the `pm` skill), then **Read next** → `mstar-harness-core` → `project-manager.md`.
- Install (user-scoped, recommended): `omp plugin install @mstar-harness/omp`, or `npx @mstar-harness/cli init --target omp --scope global` (links `~/.mstar/harness`). Project scope: `omp plugin install @mstar-harness/omp --scope project` or `npx @mstar-harness/cli init --target omp --scope project`. Afterwards `omp plugin list` shows package **`@mstar-harness/omp`** (npm) or **`morning-star`** (root `package.json` name, link path) — reload / new session to pick up skills, commands and agents.
- Local maintainers: `omp plugin link /path/to/mstar-harness/packages/omp` (or the CLI-managed `~/.mstar/harness/packages/omp` checkout) — the linked package tree resolves the engine via the workspace member, so run `bun install && bun run engine:build && bun run --cwd packages/omp build` in the checkout first; the npm install stays the primary path.

## Runtime and upgrade

- **Runtime**: Bun-hosted plugin — the pre-hook, tools and extensions run under the host's Bun, which is **not version-gated**: the store's Node floor applies to Node entrypoints only and `engines.bun` declares the development toolchain (floor semantics → `_shared/host-runtime-contract.md` § Node floor). The runtime is detected as Bun before its emulated `process.versions.node` can stand in for it; a runtime without the native `node:sqlite` capability refuses actionably instead of degrading to a transport or JSON.
- **Upgrade / reload**: reinstall or relink the package, then start a **new host process** to load a refreshed **extension registration**. On the readable OMP **18.3 SDK**, a new chat/session in the same process retains the loaded registration while `/reload-plugins` (omp ≥17.2.11) or a new session with a `?mtime` cache-buster refreshes skills/command assets, not native extension closures; source edits alone replace neither — SDK-scoped evidence, not a claim about unknown live **18.8** replacement mechanics or every hook's lifetime (§ In-process engine binding). The readiness flip that precedes an authority change → same file § Readiness, not an action.

## MCP delivery

- **Native install and loading**: `omp plugin install @mstar-harness/omp` (or `npx @mstar-harness/cli init --target omp`); the server is the CLI `mcp` subcommand → `_shared/host-runtime-contract.md` § MCP delivery, which also owns the context boundary and doctor semantics (`mstar-harness doctor --target omp`; H2's native bridge and package server are removed).
- **Native registration vs MCP**: `mstar_coordinator`, `mstar_model_handoff` and `mstar_phase2` are registered in-process from manifest `omp.extensions`; `mcp__morning_star_mstar_*` tools come from the separately launched public CLI MCP server. Independent surfaces: the public coordinator route can use an independently acquired session identity, but refreshing either surface proves nothing about the other's loaded registration.
- **Native session identity**: `extensions/mcp-identity.ts` (published as `.js`) injects the calling session's native `sessionId` into an eligible `mcp__morning_star_mstar_*` call when the SELECTED `action` declares it — a published tool is a folded family publishing its selector once for the whole tool, so the per-action fact comes from the schema's `x-mstar-selectors` index, and an action declaring no selector is left untouched and reaches the CLI exactly as the model sent it (injecting one there would make the CLI refuse the call and its "drop `sessionId`" recovery unactionable). The HOST's id always wins: a caller-supplied `sessionId` on a declaring action is REPLACED, never honored, because on the opted-in connection that wire value becomes the execution identity — deferring to it would let one agent act as another live coordinator session. Leaf sessions supply their own id, not the parent's; identity-consuming commands (e.g. `session.recover`) receive that per-call argument, mirroring CLI `--session-id`, and injection grants no workflow authority.

## Skill loading

1. On entry: invoke **`pm`** via `/skill:pm` → **Read next** loads `mstar-harness-core`, then `mstar-roles` → `project-manager.md` when PM is active.
2. Read `mstar-host` and this omp reference; if Plan mode is active, read `omp-plan-mode-bridge.md`.
3. Load `mstar-roles` and the active role reference, then topic skills on demand per that reference. Name skills in prompts and references, and prefer `skill://<name>/…` / `/skill:<name>` over absolute local paths unless maintaining this repository. Full skill-root table → `mstar-host` § Resolve loaded skill root.

## Internal URLs

omp resolves **internal URL schemes** natively (<https://omp.sh/#urls>), so skills and shared content stay addressable wherever omp installs the plugin — prefer URLs over absolute local paths: `skill://<name>` (a skill's `SKILL.md`) · `skill://<name>/<path>` (a file inside it) · `local://<name>.md` (shared context / assignments — prefer over pasting large payloads inline) · `artifact://<id>` / `agent://<id>` (a subagent's / a nested child's output) · `history://<id>` (read-only transcript of a (sub)agent session). `/skill:<name>` (invoke) and `skill://<name>` (Read) resolve to the same skill: put URLs in `task` assignment bodies and skill **Read next** lists so a role subagent loads the right skill regardless of install path — this is what makes cross-host skill references portable on omp.

## Tools map (default agent)

| omp tool | Harness use |
|----------|-------------|
| **`task`** | Primary dispatch — fan out one or more subagents (`agent` = live-schema id; prefer the Morning Star role id; batch via `tasks[]` + shared `context`) |
| **`ask`** | Structured clarify (options + recommended); prefer over free-form when choices are known |
| **`hub`** | Optional peer messaging / long-running process control among subagents — not a substitute for Assignment + `task` |

Ordinary I/O, search and external facts use the host's own tools (prefer grep/glob over shell find/grep; host AST/edit variants when present). OpenCode **`question`** / **`task`+`subagent`**, Cursor **Task**+`subagent_type`, and Kimi/ZCode **Agent** / **AskUserQuestion** are **not** omp tools — do not assume them.

### `task` shape

```text
task(context: "<shared batch context>",
     tasks: [{ name: "CamelCaseId", agent: "<Execute as role-id>", task: "<full Assignment body>" }])
```

Prefer the live schema every session (single-task shorthand may exist). Parallel **N** assignees ⇒ **one** `task` call with **N** `tasks[]` entries **or** **N** `task` calls in one assistant message; count emitted dispatches = **N**. **Envelope-first**: write `agent` + `name` as the first fields of each entry — the long body crowds them out and `agent` gets silently dropped (omp defaults to generic `task`, no error) → `parallel-dispatch.md` § Mandatory order. Which `agent` value to send, and the prompt binding that travels with it → **§ Role agents and binding** (the single body; nothing else in this file restates it).

## Role agents and binding (C5 / C5b — single body)

**The live `task` tool schema is SSOT every session**: exact `agent` names vary by omp version and which `agents/*.md` were discovered. Read the Available Agents list before dispatch — never invent names, never hard-code a stale table over the live list.

**Role-binding field: `agent`**, on the `tasks[]` entry (`task(context: "…", tasks: [{name, agent, task}])`). This field name is omp's; no other host's invoke tool uses it. A round that writes the role only in the prompt body has set no binding.

Selection order:

1. **Role match first** — Assignment `Execute as: <role-id>` present in the live `task.agent` list ⇒ **`agent: "<role-id>"`**. Commonly present after Morning Star plugin discovery: `product-manager`, `architect`, `frontend-dev`, `fullstack-dev`, `fullstack-dev-2`, `ops-engineer`, `prompt-engineer`, `qc-specialist`, `qc-specialist-2`, `qc-specialist-3`, `writing-specialist`. PM Acceptance stays in the primary session, never a dispatch target.
2. **Generic built-in only as fallback** when the role id is absent: `scout` / `explore` (read-only orientation, codebase survey, Prepare explore) · `reviewer` / `security-reviewer` (QC assist **only if** the matching `qc-specialist*` is missing) · `designer` (UI-heavy work when `frontend-dev` is missing) · `librarian` (external library/API research) · `sonic` / `quick_task` (mechanical, low-reasoning transcription only) · `task`, or omitting `agent` where the schema says omit means general worker (last resort).
3. **Anti-pattern** — `agent: "task"`, or omitting `agent`, while a matching role agent is listed. Host generics remain useful for non-role orientation/assist; they never replace a listed role agent for a role-owned deliverable.

**C5b — prompt binding, required even when `agent` already matches the role id** (an agent shell is not the full role prompt, and skill load is not automatic). Every role dispatch carries: (1) **`Execute as: <role-id>`** in the Assignment (harness routing SSOT) · (2) **`Act as <role-id>`** at the top of the `task` body · (3) the **skill load list** — read `mstar-roles` → `references/<role-id>.md` (or shared reference + parameters), then topic skills per that reference · (4) **`agent`** per C5.

Paste-only Assignment **without** a `task` invoke is **not** dispatch. Assignment template → `mstar-roles/references/project-manager/dispatch-and-assignment.md`; invoke shapes and counting → `parallel-dispatch.md`. PM is the primary orchestration seat via the `pm` skill (no bundled `task` target): never dispatch `project-manager` through `task`, and never launch another per-row primary.

## PM dispatch (`task`)

Harness **dispatch** on omp = one or more `task` calls with the role-binding field set per § Role agents and binding; N-parallel / 1-Assignment-1-invoke / paste-only mechanics → **`parallel-dispatch.md`**.

- **QC** — `Execution mode: sdd`: **N=3** entries, `agent: "qc-specialist"` / `"qc-specialist-2"` / `"qc-specialist-3"` when listed; each body still **Act as** its QC role + QC skill load, and a seat missing from the live schema falls back for that seat only per C5. `inline`: **N=1**. Cannot emit required **N** → **`Blocked`**.
- **SDD implement** — one implementer entry per task id with `agent` matching the implementer role when listed; task reviewer = a new entry with `agent: "code-reviewer"` (omp L2 review; not `qc-specialist*`) or `"reviewer"`/`"task"` fallback + C5b — no sticky resume unless host resume/id is available and recorded. Ready-task scheduling → `parallel-dispatch.md` § SDD implement. Independent ready implementers use isolated parallel tracks; never share a writable worktree or session.

## Clarify

Prefer **`ask`** for 1–3 high-impact choices with known options (`recommended` when there is a default); the fallback is one concise Markdown question after codebase exploration cannot answer it. Plan approval in Plan mode follows **`omp-plan-mode-bridge.md`** — a casual `ask` is not plan lock. "Question asked" ≠ clarify done; blocking ambiguity → **`Blocked`** or escalation.

## In-process engine binding (omp ≥ 17.2.11)

- **Surfaces** (npm package root = plugin root; sources in `packages/omp/src/`): `hooks/pre/mstar-gates.js` — one `tool_call` pre-hook returning `{ block: true, reason }` (the structured refusal the model sees as the tool error) or `undefined` (pass); the manifest `omp.extensions` lists `extensions/model-handoff.js` (model handoff + identity), `extensions/phase2-orchestration.js` (Phase-2 reminder + bind/checkpoint/read-only-history observer, `mstar_phase2`) and `extensions/mcp-identity.js` (native sessionId supply). omp discovers `hooks/` by convention from the installed package root (`<pkg>/hooks/pre/`), not `dist/`; extensions load from the manifest. No `tools/` directory or separate validator tools — validation uses the CLI/MCP surfaces.
- **Enforcement semantics**: block ONLY under `Enforcement: hard`. Both gates read the repo `.mstarc` `[config] enforcement`, else the harness compass frontmatter (`enforcement: hard`, active/locked iterations only); the dispatch gate ALSO honors each Assignment's own header flag (`assignmentHeaderRegion` — a body example never hardens), so a hard repo setting hardens flag-less dispatches (Gate 1 / dsh `resolveDispatchHard` parity). Soft-mode dispatch violations are warn-logged through the extension logger (never blocked) and soft status-write violations stay a silent pass; rollback = unset the flag (or `.mstarc` `soft`), never global.
- **Anti-recursion scope (issue #156)**: the engine's `antiRecursionPrecheck` is caller-scoped, comparing the DISPATCHING agent's own role with the new Assignment's `Execute as`. omp's `tool_call` event carries no caller identity and the task entry `agent` is the spawn TARGET — equal to `Execute as` on every compliant dispatch (C5) — so Gate 2 does NOT run the precheck here (the pre-#156 wiring hard-blocked every compliant hard-mode dispatch on `self-type`, or on `empty-binding` when `agent` was omitted). The NEVER red line stays prompt-level (`mstar-dispatch-gates`); dsh enforces it in-engine via Config `dispatchBinding`.
- **Engine dependency**: the npm package bundles the engine inline into its hook and engine-backed extension bundles at build time — zero runtime package resolution, so module link cannot fail on a missing package (the hotfix for the bare-import load failure). The maintainer `omp plugin link` path still resolves the engine via the workspace member, so build the checkout first.
- **Loaded entry vs installed inventory**: a native refusal's `loadedEntry` is sanitized provenance of the entry that actually answered. An installed package tree, `omp plugin list`, doctor manifest checks or an aligned `mcp.json` are inventory/configuration evidence, not proof of the loaded native entry.
- **Graceful degradation (explicit)**: module load failure leaves extension tools skipped and the hook absent (no blocking), with the `commands/*.md` shell-out fallback intact — but a partial failure is SILENT, with no in-band signal that gates are off; verify with `omp -p '/extensions'`.
- **`MSTAR_HARNESS_DIR` override / `.mstarc`**: the hook discovers `{HARNESS_DIR}` via `resolveHarnessDir` — a repo `.mstarc` `[config] harness_dir` (gitignored local config) first, then the probe `.mstar/` → `.agents/` → `.plans/`/`plans/`. A non-standard harness root can declare it in `.mstarc` or MUST export `MSTAR_HARNESS_DIR` (absolute path) in the omp session env; without either, the status gate does not cover those roots (parity with the opencode binding).
- **Edit-path limitation**: the status gate validates the on-disk file for `edit` events (pre-edit state), so a corrupting edit is caught by the next write or by `mstar status validate` (known v1 limitation, parity with opencode).
- **Engine version compatibility**: the hook degrades gracefully until an engine release exporting both `composeDispatchGate` and `parseCompassFrontmatter` (2.0.2 predates both). Missing exports never fail module load: on older engines Gate 2 is skipped with a one-time warning while Gate 1 stays active, and CLI/MCP validation remains available through `mstar dispatch validate` and `mstar iteration gate`.

## Model handoff (native settings)

An extension entry from this package: `extensions/model-handoff.js` (manifest `omp.extensions`; engine inlined, its single `@oh-my-pi/pi-coding-agent` import resolved by the running host). It is a **coordinator model policy owned by native settings**, not a user command — no session, flag, goal or prose can enable it. The same entry registers the coordinator **identity** tool `mstar_coordinator` (§ Coordinator identity) — an identity entry, not a model policy, so no setting here governs it.

| Surface | Contract |
|---|---|
| Native path | `/settings` → **Plugins** → **`@mstar-harness/omp`** — the rows are the schema keys: `modelHandoff` (boolean, default `false`) and `handoffTarget` (`@default` \| `@smol`, default `@default`). No activation command, no harness settings file, no second settings UI. |
| Persistence / scope | Host plugin settings (user-scope `omp-plugins.lock.json`, plus project `plugin-overrides.json`), reread through the exported helper at entry **and again at fire time** — a mid-flight enable never retro-arms an iteration already under way, and disabling at fire time suppresses the switch without terminalizing the binding. That panel lists **user-scope** installs only: a project-scope npm install has no native row (host limitation, documented rather than worked around), so use the user-scope path — never double-install or add a private settings parser/UI. |
| Supported entries / inert contexts | `/iteration-start`, `/iteration-loop` and native skill-start as labelled by input; no-argument `/iteration-drive` resumes the coordinator's iteration and never arms a new model handoff, and unsupported arguments refuse rather than broaden scope. Inert: ordinary chat, unrelated commands, leaf/subagent sessions, other hosts and an iteration whose coordinator never armed. |
| PM binding | `mstar_model_handoff` at the two anchors that own it — `direction-lock` (`{operation:"start"}`) and `phase-1-lock` (`{operation:"phase1-complete"}`); parameters, prerequisites, refusal codes and readiness → § Host hooks. Session identity, cwd, entry route, task-session state and coordinator authority are host-derived from the session ledger and the addressed root's ACTIVE execution authority, never from the call. |
| Ownership | One explicitly named workflow and control root own the coordinator. Missing, foreign or ambiguous ownership fails closed — no `workflows[0]`, latest-mtime, unique-new-row or "most recent" inference, and a concurrent sibling iteration stays untouched. Only the bound coordinator session changes model; role mappings, other sessions, subagents, goal objective and workflow lifecycle status are never written. |
| Cancellation | While pending, an unowned model change — history or live model — cancels the not-yet-executed switch, and the arm's own transition can never cancel it. Cancellation is deliberately conservative (it can also catch another extension's change; there is no exact user-selection event) and never clears the saved preference. Navigation arriving during an invoked action is refused immediately; navigation arriving first fences the action instead of letting it start. |
| Replay | Full session ledger with exact session-id filtering. A persisted attempt with no recorded outcome restores as `uncertain` — never retried, never reported as a successful handoff because the current model happens to match. Tree/branch/reload replay the ledger; a fork or new session id inherits nothing. |
| Failure visibility | Refusals appear in the tool result, state transitions also as a durable session notice; the session keeps the model it actually has and there is no automatic retry loop. Missing auth, an unresolvable role and missing evidence are reported as failures, never as a handoff. |
| Modes | Arming is observed from the host's `input` event, so it is documented for the interactive entries above only — no print/JSON/RPC automatic-behaviour claim exists (E1 boundary). The completion checkpoint is an ordinary tool call whose result the host renders like any other tool result. |

Do not describe this feature as a `pause` flag, as a goal, or as a switch performed by any other session, and do not require a provider-side or upstream change to use it.

## Phase-2 scheduling observation

`extensions/phase2-orchestration.js` supplies a bounded coordinator advisory and the `mstar_phase2` observation tool; native background task dispatch is the only task transport, and this extension never launches another primary, merges, changes engine workflow state or releases exclusion. It is Phase-2/coordinator-only and independent of model-handoff preferences: no extra-primary setting, capacity counter or terminal transport exists, it emits at most one advisory for a changed opportunity observation at agent_end (never polling or duplicating native job completion), a null snapshot means unavailable rather than no jobs, and the advisory points at the shared rescheduling checkpoint while asserting no plan ready list.

PM calls: **`bind`** — exactly `{operation:"bind", workflowId}` at phase-2-entry, with the host deriving its own native identity and canonical control root and adopting the ACTIVE DB coordinator binding (no session path/token/role is caller-supplied) · **`checkpoint`** — `{operation:"checkpoint", reason, decision, note}` at each shared rescheduling checkpoint, where the runtime attaches the sampled observation key, the reasons are the five frozen shared names, decision is dispatched/wait/blocked, and blocked suppresses continuation until a new explicit user turn or later checkpoint (never a timer) · **`export-history`** — read-only `{operation:"export-history", workflowId}`, exporting this carrying session's own observation history; it opens no file, starts/stops nothing, grants no authority and attests no quiescence, so it is source evidence only, not installed-deployment adoption or operational stop proof. Native task completion delivery stays authoritative.

## Host hooks

The four **host hook anchors** — `direction-lock`, `phase-1-lock`, `phase-2-entry`, `rescheduling-checkpoint` — and their shared carrier locations are defined host-agnostically in `mstar-host` § `## Host hooks (anchor contract)`; shared skills carry only the marker plus a one-line pointer and declare no host action. **This section is the OMP declaration for all four**: when the shared step carrying an anchor is reached, the PM executes the call declared here. Tool names, parameters, refusal codes and settings keys for these two mechanisms live in this file and nowhere else.

### Coordinator identity and session association (host → `plan bind`)

Two comparisons this surface makes — the `phase-1-lock` readiness checkpoint and the `direction-lock` start-authority scan — compare the **engine** session id with the **host** session id, so they are one identifier only when the engine adopted the host's own. This host closes that gap by **acquisition**, never by injection: a coordinator identity is explicitly acquired and the extension hands the host's native id straight to the engine. Coordinator bootstrap stays limited to one per workflow.

**Managed bootstrap — `mstar_coordinator`.** The only advertised managed route, registered by `extensions/model-handoff.js` and independent of the `modelHandoff` setting. All three operations run against the addressed root's ACTIVE execution authority, never a file route:

| Operation | Call |
|---|---|
| `bind` | `{operation:"bind", workflowId, expected, operationId}` — `expected` is the workflow's **full execution token** and `operationId` the replay key; BOTH may be omitted, and an omitted token is resolved by the engine from the workflow's own header so an identical retry is the replayed receipt (a supplied token stays a strict CAS) |
| `show-recovery` | reads the DB workflow/session state, writing nothing |
| `recover` | `{operation:"recover", workflowId, priorSessionId, reason, attestation, expected, operationId}` under an independently acquired coordinator identity |

- **The call is a lookup, never a credential.** The `bind` input carries no session path, no session id and no root: the adapter takes the **native** session id from the host session manager and the canonical control harness root from the host cwd, and the reference it returns is a stored row — a copied or stale one refuses in the engine's own caller comparison. A session id, root, caller role, authority flag or credential path has no home in the schema, and the adapter refuses any extra key by name (`forbidden-field`). Refusals: identity-missing, leaf-session, harness-not-found, invalid-input and unchanged applicable engine codes; success is bound with the coordinator reference; mixed or partial key sets refuse, never fall back.
- **The shell route refuses**: a `plan bind --coordinator` inside `bash` / `functions.bash` is refused *before* execution with a redirect to this tool, and nothing is injected for shell calls, so an absent or unsupported `env` field cannot produce an input revision; unrelated shell calls are untouched. MCP sessionId injection is the separate `mcp-identity` extension: because a shared MCP connection publishes no caller identity unless the launcher opts in, omp's packaged `mcp.json` launches the server with `--trust-caller-session-id` — the deployment-level opt-in that owns that trust — and on that connection the injected value is a bearer identity selecting the caller's own coordinator binding, while authorization stays that binding row plus the optional `--expect` CAS token.
- A local operator uses the coordinator-only CLI bind — `mstar plan bind --execution --workflow <id> --coordinator` with applicable checked context; no row-specific binding remains. Identity checks are unchanged: absent or foreign association refuses before writes and a leaf/subagent session refuses outright. One host session carries only its workflow coordinator binding; resume is read-only lookup, never re-identification or stopped-owner replacement, and a new host session identity does not inherit an existing binding. Replacing a recorded holder uses the supported coordinator recovery (`mstar_coordinator {operation:"recover"}` or CLI `mstar session recover`) with authorization to stop the exact prior holder and the applicable stop attestation/proof — never a restart, another `bind`, or a document edit.
- **Diagnostics.** Broad codes keep their names; the adapter attaches a typed subreason so causes stay distinguishable — identity detail `identity-missing`, `identity-mismatch`, `foreign-owner`, `recovery-not-prepare`, `recovery-stale`, `recovery-unauthorized`, and path detail `plan-pointer-invalid`, `plan-identity-mismatch`, plus a genuinely `prepare-unlocked` compass, never a malformed row pointer reported as an unlocked Prepare. Safe detail renders the workflow/plan, identity-source labels, already-public expected/current ids, the canonical base and target and the next supported operation — never credentials, session JSON or environment payloads.

### Auto-trigger boundary — the diagnosed failure mode

Neither extension ever arms, binds or checkpoints by itself. `extensions/model-handoff.js` observes the host `input` event only to **label** the entry route (`/iteration-start`, `/iteration-loop`, `skill-start`) — "It never authorizes anything"; arming happens **only** inside the `mstar_model_handoff {operation:"start"}` handler, with its authority derived host/engine-side (task-session ledger, the addressed root's ACTIVE execution authority, the root register), never from the call. `extensions/phase2-orchestration.js` emits its bounded advisory **only after** a recorded `bind`, and `{operation:"checkpoint"}` likewise requires a live binding. `mstar_coordinator {operation:"bind"}` is an explicit PM call made when a workflow needs its coordinator session — no host event, entry route or setting performs it, and it stays a no-op on this feature's ledger. Enabling modelHandoff never retro-arms an iteration; the preference is read at entry/fire and disabling suppresses the model action without rewriting binding; Phase-2 observation has no extra-primary settings and starts only after the coordinator's explicit bind.

### Coordinator-visible notices

Both mechanisms emit durable, coordinator-visible notices under one visible bar title, **`mstar:notice`** — the Phase-2 diagnostics (`extensions/phase2-orchestration.js`) and model-handoff transitions (`extensions/model-handoff.js`) — while the bounded Phase-2 advisory carries **`mstar:advisory`**. The bar title is the `customType` literal (OMP has no separate title field). The hidden durable ledgers keep their own types — **`mstar:phase2`** for this feature's decision records and **`mstar:model-handoff`** for handoff records — never a visible notice name (`mstar:model-handoff` is never reused as one).

Every notice renders through the shared shape `<title>: <detail>` with the observed condition or refusal code preserved in the detail; a detail opening with the title's own sentence renders as the title plus that detail's remainder, so a status sentence is never stated twice. **Status-bearing title** — when the workflow's own lifecycle status was read from the ACTIVE authority at notice time, the title states the workflow id plus its actual lifecycle status verbatim (`Workflow <id> is <status>`), reporting workflow lifecycle status only, never the workflow's phase, a refusal code, or the model-handoff ledger state (`pending`, `cancelled`, `handed_off`). **Fallback title** — when no readable authority state supplied the id/status, the title states only the observed operation or condition (`… needs attention`) and asserts no workflow status; missing or unreadable status evidence never suppresses a notice and never substitutes a guessed `running`/`completed` value. A terminal workflow refuses `phase2.workflow-terminal` with its observed status, and no notice or refusal text on either path carries a fixed inactivity prefix or a detail sentence asserting a current Phase-2 position. The Phase-2 diagnostic path stays deduplicated by code per generation — at most one notice per distinct refusal code until the generation resets; model-handoff notices do not share that dedup mechanism.

#### `direction-lock` — `mstar_model_handoff {operation:"start", workflowId}`

- **Exact parameters**: `workflowId` (string, required) — the only caller-supplied field that matters here; `mainWorktreeBranch` is accepted by the schema but unused on this path. Authority, entry route, intent and task-session state are host-derived, never call-declared, and the strict schema refuses an extra key (a session path or envelope) rather than ignoring it.
- **Two ACTIVE routes (host-derived)**: the public tool keeps `{operation:"start", workflowId}` — no mode, session credential or authority claim is accepted from the caller — and the adapter classifies the addressed workflow from the validated ACTIVE authority for that explicit id, never from a newest/unique-workflow inference. **Registered running iteration** → the arm route: the named workflow's ACTIVE lifecycle and this host session's coordinator seat are revalidated, then the host-local pending binding is recorded from the adopted execution binding. **No ACTIVE lifecycle for that id, or a non-running/non-iteration one** → `register-invalid` (`the execution authority holds no ACTIVE lifecycle for the named workflow; a new start addresses the DB's own workflow view and never reserves an unregistered id`), and a seat held by another session → `coordinator-elsewhere`; neither path reserves, writes or falls back. No `coordinatorSessionPath`-style envelope input exists in the schema, and neither branch introduces a new refusal code or public tool mode.
- **Required or optional**: the PM reaches this anchor once and makes the call; when native `modelHandoff` is off the tool returns a **success-shaped no-op** (`isError: false`, no binding/model switch) with a neutral notice and needs no repair or re-enable prompt. When enabled, the ordinary coordinator identity and ACTIVE-binding checks still apply — do not infer readiness from the preference alone.
- **Other no-op/refusal outcomes, and authority**: `already-bound` remains a real binding conflict in this session; `suspended` / `in-flight` report the observed navigation/action state. They are not the preference-off result and cannot be bypassed by toggling settings. Authority refusals (task-session, coordinator-elsewhere, binding-invalid, register-invalid) retain their meanings: host/engine facts derive authority, never the call; the addressed workflow's ACTIVE lifecycle and this session's coordinator seat are re-read at the call, and a missing or foreign one refuses by name while unrelated workflow ownership still refuses.
- **Visible arm failures** (reported as failures; **no automatic retry**): `settings-read-failed` · `record-failed` · `slow-unresolved` · `slow-selection-failed` · `slow-selection-refused` · `arm-evidence-conflict`. **Host-level**: `tool-error` (the tool threw without touching model, ledger or engine state). **Success code**: `armed` (state `pending`) — the coordinator holds it until `phase-1-lock` fires or the handoff is cancelled.

#### `phase-1-lock` — `mstar_model_handoff {operation:"phase1-complete", …}`

- **Exact parameters**: `workflowId` (must equal the bound workflow) · `mainWorktreeBranch` (string — the recorded primary-checkout branch, distinct from the integration branch) · `reviews[]` — one to three selected specialist returns in Phase 1 order, ending with the required `writing-specialist` (`product-manager` and `architect` returns are optional) · `plans[]` — **at least one** bound-plan evidence entry. The strict schema carries no session path or envelope field: the ACTIVE DB binding is the authority. Frozen-input shape validation applies only with the preference enabled and a pending binding — missing or invalid completion input is refused, never inferred; with the preference off, `{operation, workflowId}` alone returns the `preference-off` no-op without requiring completion evidence.
- **Required or optional, and the preference read**: the PM reaches this checkpoint and makes the call. `in-flight` is checked before the preference is read and can refuse in any preference state; `settings-read-failed` reports a failed preference read; `preference-off` is not an error — regardless of binding state it is a success-shaped no-op (`isError: false`, no binding created, unchanged model/binding) with a neutral notice, and never a reason to ask the user to re-enable it, re-arm, or repair a deliberately disabled preference.
- **Readiness prerequisite (all four, re-checked at fire time)**: the sequential specialist returns for that iteration; the PM-confirmed Prepare gate for every registered plan with `compass status: locked`; a distinct same-repository integration checkout on its recorded branch; a remote tip equal to the validated integration HEAD. `evaluatePhaseGate` is a later-phase gate and is never readiness evidence; a draft compass, a lock alone, a missing checkout or an unpushed commit is not ready. This checkpoint also compares the registered `compass_ref` with the bound compass document: a row that stores no pointer reports `compass-unregistered`, a pointer naming another document or spelled repository-relative (`.mstar/...`, joined under the harness root into `.mstar/.mstar/...`) reports `compass-pointer-invalid`, and one of the two authored anchors disagreeing with the registered workflow reports `compass-base-branch-mirror` / `compass-integration-branch-mirror` / `compass-worktree-mirror`. Every one of those diagnostics names its own repair: correct the pointer with `mstar workflow compass-ref --workflow <id> --compass <harness-relative-or-absolute-compass> --reason <why>`, or add the named frontmatter field so the authored compass mirrors the registered anchor, then re-run the checkpoint. The pointer is only ever compared — the checkpoint never rewrites the registry.
- **Enabled binding/completion path**: `not-pending` (no pending binding; error, unreachable when the preference is off) · `binding-mismatch` · `invalid-completion-input`. With a pending binding, `not-ready` names the unmet readiness facts and leaves it unchanged; `suspended` and `record-failed` retain their specific diagnostics.
- **Terminal refusals** (**no retry**; the session keeps the model it actually has): `cancelled` (an unowned model change arrived while pending; not an error) · `target-unresolved` (`handoffTarget` unresolvable) · `switch-refused` / `switch-threw` (the host refused the selection). **Host-level**: `tool-error`. **Success code**: `handed_off` (state `handed_off`, with the actual model reported).

#### `phase-2-entry` — `mstar_phase2 {operation:"bind", workflowId}`

- **Exact parameters**: `workflowId` alone, plus `operation`. The request object is strict — **no session path, session reference, token, caller role or authority claim is accepted** — and authority is derived host-side, never from the call: the host session id, the canonical control harness root, the accepted phase and the checkout root are all re-read, and the identity pointer is adopted from the addressed root's own ACTIVE authority (the DB coordinator binding, resumed against the current store/epoch before it is recorded). An extra or missing key refuses instead of selecting a fallback authority.
- **Required / prerequisite**: record only the coordinator observation identity pointer, no engine state or credential — ACTIVE bind records `{version:2,kind:"bind",hostSessionId,workflowId,executionBinding}`, and historical file bindings never become DB bindings by inference. The workflow's recorded phase must be `phase-2-execute` (an unknown or missing phase disables the observation), the caller must sit on this workflow's coordinator seat, and the caller's checkout must be the main worktree or the recorded integration worktree.
- **Refusals** (visible; **nothing bound**): `phase2.task-session` — a leaf/subagent (`session_init`) session, or a session with no id · `phase2.harness-not-found` · `phase2.authority-unreadable` · `coordination.workflow-not-found` · `phase2.coordinator-mismatch` (the ACTIVE authority's coordinator seat is another session) · `phase2.scope-mismatch` (the caller's checkout is neither the main worktree nor the integration worktree) · `phase2.binding-stale` (the adopted DB binding no longer authorizes this session) · `phase2.record-failed` · `tool-error`. **Non-failure**: `already-bound` (`applied:false`) — an identical re-bind is idempotent, the pointer unchanged and the call safe to repeat. **Success code**: `bound` (`applied:true`).

#### `rescheduling-checkpoint` — `mstar_phase2 {operation:"checkpoint", reason, decision, note}`

- **Exact parameters**: `reason` — **one of the five frozen names, verbatim**: `before-wait`, `result-settled`, `dependency-changed`, `ownership-changed`, `capacity-changed` · `decision` ∈ `dispatched | wait | blocked` · `note` (string, required). The argument schema is a strict union: any other value is rejected before anything is written. The runtime attaches the sampled observation key — the caller cannot choose or reset it.
- **When**: **one call per** re-evaluation of the shared `Rescheduling checkpoint` (`mstar-iteration/references/phase-2-worktree-lease.md` §2.4) — a call acknowledges that PM ran the shared scheduling procedure against the sample taken at that moment. **Required** per re-evaluation, never batched into the next one and never skipped because "nothing changed"; a checkpoint carries a decision and a note, never a ready list. **Prerequisite**: a live `phase-2-entry` binding in this session — the ownership probe is re-run on every call.
- **Refusals** (visible; **no checkpoint recorded**, advisory state unchanged): `phase2.not-bound` (run `phase-2-entry` first) · `phase2.record-failed` · `tool-error`, plus the ownership-probe codes shared with `bind`: `phase2.binding-stale` (the adopted DB binding no longer authorizes this session) · `phase2.ownership-drift` (the ACTIVE coordinator seat no longer belongs to the bound session — re-run `bind`) · `phase2.authority-unreadable` · `phase2.harness-unresolvable` · `coordination.workflow-not-found` · `phase2.workflow-terminal` · `phase2.phase-inactive` (the workflow left `phase-2-execute`). Both stale codes mark the local binding not-current and tell the PM to re-run `{operation:"bind"}` before relying on this session.
- **Success code**: `recorded` (with the returned `observationKey` and `blocked` flag; `blocked` suppresses advisory continuation until a new explicit user turn or a later checkpoint — never a timer or incidental snapshot churn). **Advisory sample refusal**: `phase2.snapshot-unavailable` means unavailable, never no jobs; the observer does not read deleted extra-primary preferences.

## Files, shell, git and evidence

- Prefer host search/edit tools over shell find/sed; respect omp approval prompts (`approval-mode`, write/yolo) for destructive operations; do not edit `~/.omp/` credentials, plugin lockfiles or user secrets without explicit consent.
- Git follows `mstar-branch-worktree` and the Assignment **Working branch** / **Branch policy**; completion reports cite concrete commands, artifacts and commit lines when required.
- Native task isolation (`task.isolation`) or `~/.omp/wt` remains host-owned: assignments record canonical absolute source paths/branches under the authorized sibling-root worktrees and ordinary row metadata, and host isolation never grants coordinator state authority.

## Gotchas

- Installed npm plugin package name is **`@mstar-harness/omp`** (git/link path root **`morning-star`**); the Morning Star display name remains **morning-star-harness**. Marketplace (Claude) installs and `omp plugin install` are different discovery providers — prefer one install path per machine to avoid duplicate skill listings.
- Session plan UI / todos are not durable SSOT unless mirrored to `{HARNESS_DIR}`.
- After install/link, **reload / new session** so `agents/*.md` appear in the live `task.agent` list — stale sessions may only show host generics and wrongly push you to `agent: "task"`.
- **Sequential N=1 Review-&-Edit turns are where `agent` gets dropped**: the "all N in one message" pressure is absent and the count gate passes trivially — re-verify **`agent: "<Execute as>"`** on every single dispatch; `tasks:[{task:"…"}]` with no `agent` is a silent generic fallback, not a valid role invoke.
- omp has no `sessionStart.skill`, so new sessions do **not** auto-load PM — invoke `/skill:pm` manually. Do not confuse omp **`task.agent`** with OpenCode **`subagent`** or Cursor **`subagent_type`**, and do not treat Kimi/ZCode "built-ins only → always `coder`/`task`" habits as omp defaults when Morning Star role agents are listed.
