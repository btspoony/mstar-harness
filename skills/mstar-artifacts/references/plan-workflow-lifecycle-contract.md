# Plan workflow lifecycle contract

The authoritative semantics for plan-level workflow delivery: what a `type: plan` workflow declares at registration, the stages it walks, the evidence each stage owes, and the engine seams that enforce them (§6). Corpus surfaces cite this file pointer-level instead of restating it; where a skill's prose and this contract disagree on lifecycle semantics, this contract is the wording authority.

Execution authority is the ACTIVE DB route in `{HARNESS_DIR}/store.db` (`execution_registry`, `execution_workflows`, `execution_plans` and the other execution tables); a harness with no ACTIVE store has no execution authority (conversation tracking) and never falls back to files. The predecessor file route — create-only snapshot plus root `workflows[]` registration with snapshot-terminal close ordering — is retired history, not a live route or a second transport.

Two distinct units: a **standalone plan workflow** (one registered lifecycle with its own declared delivery obligation and terminal close) and a **plan row inside an iteration** (a work unit coordinated by the iteration's primary PM; row completion creates no child PR obligation or secondary PM seat). Four facts are not interchangeable: plan-row `Done`, workflow `completed`, PR opened, PR merged — a workflow with completed implementation but an outstanding delivery PR stays active and resumable.

## 1. Delivery-kind declaration

Every workflow declares its delivery kind at registration (§4a); it is recorded then and never inferred retroactively from runtime behavior, field presence or convenience. Missing fields never select a kind and never waive the declared obligation — a `development` workflow with missing branch fields is incomplete registration, not an exempt workflow, and a report-only workflow follows its recorded policy, never a PR exemption inferred from absent fields. An iteration uses the same outer lifecycle around its plan rows; child rows are not standalone workflows and gain no independent delivery PR obligation.

- **`development`** — the full §3 lifecycle applies: PR submission, merge-ready milestone, verified merge and evidence-backed terminal close; the PR obligation is the declared delivery path, not an optional extra.
- **`verification/report-only`** — an explicit alternative completion policy is recorded at registration: a registration-time declaration of what the deliverable is, not a fulfilment payload. Direct completion and the evidence-backed terminal close need only QC/QA under that registered policy, plus every row `Done`; no fulfilment payload is recorded, and no Git/integration, compound-before-PR, PR or merge obligation is invented.

## 2. Cardinality stance

The normal route is **one independently owned development plan per `type: plan` workflow**; the type label alone does not establish cardinality. Producers are `mstar workflow register` / `mstar iteration register` through the store-backed registration seam (§4a); there is no second registration mechanism.

## 3. Lifecycle stages

The common delivery lifecycle: `register → recall → prepare/lock → execute + review/acceptance → compound disposition → submit PR → merge-ready (milestone) → prove merge (local association) → terminal close/unregister`. Per stage: **register** records delivery kind and execution identity and does not authorize implementation — advisory research and unselected candidates are never silently promoted; **recall** records a receipt of relevant knowledge inputs (reused and rejected decisions, or a truthful empty result) before plan lock — no full-corpus scan, no invented knowledge; **prepare/lock** keeps the existing Prepare/clarify gates (`mstar-phase-gates`), whose ownership and risk rules are unchanged; **execute + review/acceptance** records the per-plan gate evidence (implementation checks, QC tri, QA gate) — row `Done` is not workflow completion; **compound disposition** records outcome ∈ {`created`, `updated`, reasoned `skipped`} on the delivery branch/worktree before the PR head is finalized — high overlap updates an existing document rather than duplicating; **submit PR** derives its identity from the registered delivery anchors (head `branch.work`, target `branch.target` — §4d), so nothing about it is recorded — a local commit or pre-existing unrelated PR does not satisfy it; **merge-ready** is a resumable milestone, never a completion state; **prove merge** is the local Git association rule (§4f) run by both the close and the read-only Phase-6 gate — opened, mergeable and merged are different facts, and reachability alone is not proof; **terminal close** is §4g. Every stage transition records its evidence; failure leaves rows and workflow blocked/active, never silently done.

**Iteration and route application.** One primary coordinator drives its rows through ordinary operations with dependency scheduling, isolated leaf tasks and serial real integration; child completion never triggers a child delivery PR or premature parent closure, and only the parent walks compound → submit PR → prove merge → terminal close. The engine selects the row's completion route from the workflow's own `type` and declared delivery kind — never from anchors that happen to be absent:

| Route | Selected when | Direct completion proof | Outer obligation |
|---|---|---|---|
| iteration | Non-standalone workflow | QC/QA/source-review proof plus the already-performed serial merge `integration: {base_sha,result_sha}` verified against the recorded integration checkout/target and ancestry | Row Done only; parent compound/merge proof/close |
| standalone development | `type: plan`, `delivery_kind: development`, exactly one row | QC/QA plus clean registered source checkout/ref and commit; integration input refuses | Row Done precedes own compound/merge proof/close; workflow stays running |
| standalone report-only | `type: plan`, `delivery_kind: verification/report-only`, exactly one row | QC/QA under the registered completion policy; no fulfilment payload, no invented Git; integration input refuses | Row Done precedes the terminal close, which consults the registered policy and QC/QA; no PR/merge |

All routes use coordinator `complete` — no per-row bind, sealed Assignment or ownership-transfer protocol exists, and missing anchors never select another route. QA/cleanup configuration defaults to mandatory/allow-residual and is revisable through ordinary prepare; recorded source metadata/defaults need no ceremonial prepare record. Direct complete re-witnesses relevant Git at commit, retains source metadata, releases the applicable workflow merge exclusion in its verified transaction and preserves replay timestamps; evidence hashes record provenance, not byte-level plan or Assignment admission. A released exclusion is an audit record, not permission to resume or take another owner's claim.

## 4. Evidence contracts

- **(a) Registration** is an authorized domain operation through the store-backed registration seam: `mstar workflow register` / `mstar iteration register` consume the root creation token and an operation id, record the declared delivery kind and execution identity, and write no root `status.json` or workflow snapshot. Workflow writes use workflow tokens and plan writes plan tokens; session references select an independently acquired caller identity, never authority supplied by a leaf. A failed register write is never partial activation; crash/retry preserves identity, timestamps, ownership and resumability without duplicating identity.
- **(b) Admission consumes registration** (seam S2): execution without a registered running workflow row is refused with a precise refusal code that names the registration command and the recovery path — never silently continued on branch alignment alone.
- **(c) Compound disposition** outcome ∈ {`created`, `updated`, reasoned `skipped`} is recorded before PR head finalization; engine checks validate the disposition and referenced artifacts — that is not semantic-quality proof — and existing compound document/index validation is reused as-is. **(d) PR identity is derived, never recorded**: the head is the registered delivery branch (`branch.work`, resolved through the one reader that also accepts the pre-rename `branch.source`), the target is `branch.target`, and the repository is the plan row's own recorded checkout — a recorded copy is an unused member and `delivery.pr` is refused, so a repaired anchor can never strand a frozen identity; a failed submission leaves the workflow blocked/active, not completed.
- **(e) Merge-ready** leaves the workflow registered and resumable; a requirement to submit a PR implies no authorization to merge it. **(f) Merge proof is local Git association, never a sentence.** The close and the read-only Phase-6 gate run the same rule (`verifyDeliveryEvidence`) over the plan row's recorded `metadata.worktree_path` — the first recorded checkout that resolves the target ref, so a path repointed at another clone cannot decide the proof: (1) the target ref is the fetched `refs/remotes/origin/<branch.target>`, else the local `refs/heads/<branch.target>`, remote-first because a provider merge lands in the remote; (2) the delivery branch tip (`branch.work`, its local ref first) contained in that target proves a merge commit or fast-forward; (3) otherwise every commit in `fork..tip` patch-equivalent upstream (`git cherry <target> <tip>` non-empty, every line `-`) proves a rebase or a single-commit squash with no recorded value — only while `<target>..<tip>` holds no merge commit (`git rev-list --merges` empty), because `git cherry` omits merge commits and would hide content only a merge introduced; (4) otherwise a recorded `delivery.merge.commit` — one optional full lowercase 40/64-hex commit id, the provider's squash commit — proves the delivery only when it exists as a commit, is contained in the target, AND carries the delivery's own diff, i.e. `git patch-id --stable` of `<commit>^..<commit>` equals that of `fork..tip`, where `fork` is `git merge-base <target> <tip>`. Reachability alone is NOT proof — the fork point of an unmerged delivery is an ancestor of the target too, so a recorded commit merely contained in the target is refused. Anything else refuses with the cause and a recovery: fetch the target branch into the plan checkout, restore or fetch the delivery branch ref, or record the provider merge commit through `mstar workflow evidence`. The engine queries no provider and issues no network call; a multi-commit squash is therefore not provable from patch equivalence alone and needs that recorded commit, and a delivery history carrying a merge commit in `<target>..<tip>` cannot pass on the cherry shortcut.
- **(g) Terminal close** is `mstar status workflow-close`: one store transaction writes the terminal workflow state and unregisters the workflow from `execution_registry`, consulting delivery-kind evidence first (§6 S3). Prerequisites are every row `Done`, delivery-kind evidence, and no dangling workflow integration exclusion; close never releases an exclusion to force success, runs the same §4(f) association proof as the read-only gate so the two can never disagree, and a retry after the terminal write preserves the original terminal timestamp.

## 5. Failure and abandonment

Failure and abandonment close through explicit `failed`/`stopped` statuses with a recorded reason (`mstar workflow lifecycle --status failed|stopped --reason` under the acquired coordinator identity) and are never rewritten as successfully completed; an already-terminal workflow keeps its actual status and close never fabricates `completed`. Close never releases leases — strict terminal validation refuses leases without deleting them. Leaf assignments cannot mutate lifecycle anchors or close workflows; those workflow-wide operations stay with the primary coordinator.

## 6. Engine seam inventory

Three named seams; this section specifies seams, it implements none. **S1 — registration producer**: the §4a store-backed path is the only producer; a missing registration, failed register write or ambiguous owner blocks execution without partial activation being treated as success. **S2 — admission consumption**: an unregistered plan's execution is refused, not silently continued, and the refusal names registration and recovery. **S3 — delivery-evidence consultation**: before a `completed` close the registered delivery kind's evidence is consulted — an incomplete `development` delivery (no compound disposition, or an unproven merge under the §4f association rule) refuses with `PHASE6_DELIVERY_*` and stays registered/resumable; a `verification/report-only` workflow owes no fulfilment payload, only every row `Done` plus QC/QA under its registered policy. `failed`/`stopped` closes are never demanded delivery evidence. Per-stage engine gates beyond S2/S3 stay deferred (`evaluatePhaseGate` remains iteration-shaped); those stage obligations are process obligations carried by corpus pointers to this contract.

## Migration and history

Root `status.json` and workflow snapshots are read-only migration sources / retained history. `mstar store upgrade --operator <name> --harness <control-root>` imports recognized v1/v2 execution sources directly, preserving original bytes; standalone `mstar migrate` staging is retired — the verb refuses (`migrate.verb-retired`) and names the `store upgrade` recovery; there is no staging step, internal status/snapshot writer or live file-state fallback. Each active standalone v1 plan lift requires one addressed delivery declaration using its original workflow ID — `development` with source/target branches, or `verification/report-only` with its completion policy (§1/§4a); kind is never inferred; missing, duplicate, unmatched or incoherent declarations refuse before execution rows are registered, naming the affected IDs with same-entry retry; store initialization may already have committed, so a refused call is not whole-call mutation-free; completed v1 rows, v2 snapshots and iterations need no declarations, and inapplicable ones must be omitted on retry. Exact input shape → `mstar store upgrade --help`. User-facing persist and engine `ArtifactKind` accept `review` and `json` only; `mstar harness scaffold` does not write `status.json`; notes and documents are never accepted-operation authority.

## Binding negatives

- No part of this contract authorizes auto-merge: submitting a PR never implies merge authorization; merging is a separate authorized act, proven by the local association rule in §4f.
- No forced PR for `verification/report-only` workflows: their completion follows the policy recorded at registration (§1), and their `completed` means every row `Done` plus QC/QA — not a recorded self-attestation.
- No cleanup authorization is implied by lifecycle completion: worktree/branch deletion stays explicit and ownership/merge-guarded, exactly as the existing post-merge-close contract requires.
- Close never releases leases/exclusions, and terminal `failed`/`stopped` states are never rewritten as `completed` (§5).
