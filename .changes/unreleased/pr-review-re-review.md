- **PR review now defines the re-review of the same target.** `mstar-audit` → `references/pr-review.md` gains § Re-review: when a target already has a prior report, that report is the *input*, not the scope. The reviewer revalidates each prior accepted finding and `- unverified:` item as `fixed` / `still present` / `regressed` / `not verifiable`, then reviews only the increment from the prior `head` to the new head. Covered hunks are not re-read.
- **The tally describes the current state.** A `fixed` finding leaves the tally so one defect is not penalized twice and the verdict can improve; `still present` keeps its merge class unless the increment changes reachability; `regressed` enters at its prior class; new findings come only from the increment and the fix sites. The prior `Considered & rejected` list carries forward, so a rejected candidate is not re-chased without new evidence.
- **The increment is a two-endpoint diff; rewritten history is not one.** The basis is `git diff <prior-head>..<new-head>`, valid only while the prior head is an ancestor of the new head — the three-dot form is used nowhere here, because on a rebase it replays content the prior report already judged. When the ancestry test fails (rebase / force-push), no hunk is prior-covered: the run either reviews the resolved `base...<new-head>` in full, or — with explicit operator acceptance — revalidates the prior findings against the fix commits only and declares the reduced coverage (`rebase: unchanged prior scope not re-read`) under `- notes:`. Patch-equivalence pairing is never accepted as coverage.
- **Seats get the increment pack, not the setup snapshot — unless ancestry fails.** On a covering re-review the increment is written as `increment-<prior7>-<new7>.diff` into the target's run directory from the primary checkout and passed to every seat as `--diff-file`, so the full `base...<new-head>` snapshot can never put already-reviewed hunks back in front of them; when ancestry fails the pack follows the declared path (the full diff, or the fix-commits diff). Seats also receive the prior report path and their assigned findings for revalidation. The setup sidecar and its snapshot keep their existing role for base resolution and posting coordinates.
- **Seats and tier follow the increment**, using the same sizing bands; a security-sensitive increment stays `deep` at any size, and a domain touched by neither the increment nor a revalidated finding needs no seat.
- **Report and posting.** The posted review body gains a `### Revalidated findings` subsection (`none` on a first review) and the frontmatter an optional `supersedes:` naming the prior report; a same-directory round escalates to the next `report-r<N>.md` revision, a later date starts its own run directory, and both post a new `COMMENT` review without rewriting or resolving prior threads. A prior captured issue's revalidated state is disclosed in the report — a recurrence appends an occurrence, while closing a `fixed` finding stays the issue-store authority's separate authorized act.
- **Entry surfaces agree.** `/amazing-pr-review` step 1 and the `mstar-audit` variant table route a same-target second run to § Re-review instead of re-running the whole diff.

- **PR review 现定义了同一目标的 re-review。** `mstar-audit` → `references/pr-review.md` 新增 § Re-review：当目标已有上一轮报告时，该报告是**输入**而非范围。复核每条既有 accepted finding 与 `- unverified:` 项为 `fixed` / `still present` / `regressed` / `not verifiable`，随后只审上一轮 `head` 到新 head 的增量，已覆盖的 hunk 不重读。
- **tally 描述当前状态。** `fixed` 的 finding 退出 tally，避免同一缺陷被扣两次分、也让结论有改善空间；`still present` 保留原 merge class（除非增量改变可达性）；`regressed` 按原 class 作为新 finding 计入；新 finding 只来自增量与修复点。上一轮 `Considered & rejected` 清单顺延，没有新证据不重追已驳回的候选。
- **增量是 two-endpoint diff，重写历史不算增量。** 基准为 `git diff <prior-head>..<new-head>`，仅当上一轮 head 是新 head 的祖先时成立——此处不使用 three-dot，因为 rebase 后它会重放上一轮已判过的内容。祖先判定失败（rebase / force-push）时没有任何 hunk 可视为已覆盖：要么完整审 `base...<new-head>`，要么在操作者明确接受后只按修复提交复核旧 findings，并在 `- notes:` 声明降级覆盖（`rebase: unchanged prior scope not re-read`）。patch 等价配对不作为覆盖依据。
- **席位拿到的是增量包，不是 setup snapshot——祖先判定失败时除外。** 覆盖型 re-review 由主检出把 `increment-<prior7>-<new7>.diff` 写入该目标 run 目录，并作为 `--diff-file` 传给每个席位，避免完整 `base...<new-head>` snapshot 把已审 hunk 重新摆到席位面前；祖先失败时按所选路径传包（完整 diff 或修复提交 diff）。席位同时拿到 prior report 路径与分配给它的待复核 findings。setup 的 sidecar 与 snapshot 保持原职责，仅用于解析 base 与发布坐标。
- **席位与 tier 跟随增量**，沿用同一分级带；安全敏感增量不论大小保持 `deep`，既未被增量触及也无需复核的领域不派席位。
- **报告与发布。** 发布的 review 正文新增 `### Revalidated findings` 小节（首次 review 写 `none`），frontmatter 增加可选的 `supersedes:` 指向上一轮报告；同目录轮次递增为下一个 `report-r<N>.md` 修订，跨日则新建 run 目录，两者都发布新的 `COMMENT` review，绝不改写或 resolve 既有线程。已捕获 issue 的复核状态在报告中披露——重复出现则追加 occurrence，`fixed` 的关闭仍属 issue 权威的独立授权动作。
- **入口面一致。** `/amazing-pr-review` 第 1 步与 `mstar-audit` 变体表把同一目标的再次运行路由到 § Re-review，而不是重跑整个 diff。
