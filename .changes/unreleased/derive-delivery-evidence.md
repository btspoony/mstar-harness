- **Delivery evidence no longer carries a hand-recorded PR identity.** The `delivery.pr` member is gone: the PR head and target ARE the registered `branch.work` / `branch.target` anchors (contract §4d), so recording a copy is refused as an unused member and a repaired anchor can no longer strand a frozen identity.
- **`delivery.merge` is now one optional fact: the provider commit.** The shape is `{ commit?: string }` — a full lowercase 40- or 64-hex commit id. The free-text `provider` / `evidence` attestation, which gated `completed` while nothing verified it, is deleted.
- **The merge is proven from local Git, once, for both consumers.** `verifyDeliveryEvidence` runs the pure evidence rules plus an association proof in the plan row's recorded `metadata.worktree_path` (the first recorded checkout that resolves the target ref, so a path repointed at another clone cannot decide it): the target ref is read remote-first (`refs/remotes/origin/<target>`, else `refs/heads/<target>`) because a provider merge lands in the remote and `git fetch` advances it while a local head may stay stale; an ancestor `branch.work` tip passes; otherwise every delivery commit patch-equivalent upstream (`git cherry <target> <tip>` non-empty, every line `-`) passes with no recorded value, but only for a merge-free delivery history (`<target>..<tip>` holds no merge commit, which `git cherry` never reports); otherwise a recorded `merge.commit` passes only when it exists as a commit, is contained in the target, AND carries the delivery's own diff (equal `git patch-id --stable` for `<commit>^..<commit>` and `fork..tip`). Reachability alone is not proof. Close and the read-only Phase-6 gate call the same function, so they cannot disagree; an unproven merge is `PHASE6_DELIVERY_MERGE_UNPROVEN` on both.
- **A proven close keeps its proof.** The terminal write persists the close's own association facts (`delivery.proof`: target, tip, when, and the verified commit when one was needed) in the same transaction; the read-only gate trusts that record instead of re-reading a checkout routine cleanup may already have removed, and no caller-facing payload can supply it. The diff streams to `patch-id` through a scratch file, so a large delivery fails on the association and never on a buffer cap.
- **Stored blocks stay readable.** Snapshots recorded by the previous shape keep their `delivery.pr` and free-text `merge` as history: persisted-state validation reads those members as absent instead of invalidating the snapshot (the same read tolerance the pre-rename `branch.source` spelling gets). Every write path still refuses them.
- **Refusals name the cause and an executable recovery.** An unproven merge says which relation failed — no delivery ref, a tip outside the target, commits with no patch-equivalent counterpart, an absent recorded commit, or a recorded commit whose patch id differs from the delivery diff — and points at fetching the target branch, restoring the delivery branch ref, retrying, or recording the provider merge/squash commit via `mstar workflow evidence`. No network or provider call is added; every Git read uses the existing argv-array helpers.
- **Known limits, documented rather than hidden:** a rebase or single-commit squash proves itself through `git cherry`; a multi-commit squash is not provable from patch equivalence alone (each commit's patch id differs from the squashed patch) and needs its provider commit recorded; a squash that resolved conflicts differently has no local proof, so its terminal state is `mstar workflow lifecycle --status stopped|failed --reason`; a target with no local and no fetched ref is a refusal, never a pass (a stale local head alone is not, because the remote ref is read first). Legacy `completed` snapshots re-gate under this proof; the minimal recovery is rebuilding the recorded checkout with `git worktree add` — the gate re-proof is read-only — and the durable one adds `mstar workflow reopen` (which admits exactly such an unproven history) plus one ordinary close, which then re-proves the merge and persists the proof. KNOWN GAP, stated rather than hidden: when the checkout AND the delivery branch ref are both already gone, no local fact re-establishes the association and the gate refusal stands — the cleanup contract retains a squash-only local branch so supported cleanup never reaches that state.
- `mstar workflow evidence` publishes the new shape (`merge { commit? }` — the member optional, but a supplied block must carry `commit`, which the CLI schema now also requires; no `pr`) and its help text; the deleted anchor/PR advisory warning and its close-time immutability refusal are gone with the duplicate identity.

- **交付证据不再携带手工记录的 PR 身份。** `delivery.pr` 成员删除：PR head/target 就是注册的 `branch.work` / `branch.target` 锚点（契约 §4d），记录副本会被当作未使用成员拒绝，修锚点也不会再撞上冻结的身份。
- **`delivery.merge` 只保留一个可选事实：provider commit。** 形状为 `{ commit?: string }`（小写 40/64 位完整 commit id）。原先只是自由文本、却被用来放行 `completed` 的 `provider` / `evidence` 自述已删除。
- **merge 由本地 Git 关联证明，close 与 Phase-6 gate 共用同一条规则。** `verifyDeliveryEvidence` 先跑纯证据规则，再在 plan 行记录的 `metadata.worktree_path` 内做关联证明（多个记录中优先能解析目标引用的那个，被重指向别的 clone 的路径无法决定结论）：目标引用**远端优先**（`refs/remotes/origin/<target>`，缺失则取 `refs/heads/<target>`），因为 provider merge 落在远端，`git fetch` 推进的是远端引用而本地 head 可能滞后；`branch.work` tip（本地引用优先）是祖先即通过；否则每个交付提交都已有 patch 等价的上游提交（`git cherry <target> <tip>` 非空且每行 `-`）即通过，无需任何记录值——但仅限不含 merge commit 的交付历史（`<target>..<tip>` 无 merge 提交；`git cherry` 从不上报 merge，只有 merge 引入的内容会被它隐藏）；否则记录的 `merge.commit` 只有在「真实存在 + 被目标包含 + 携带本次交付的 diff（`<commit>^..<commit>` 与 `fork..tip` 的 `git patch-id --stable` 相等）」时才通过。仅“从目标可达”不构成证明。两者不可能给出不同结论；未证明的 merge 在两条路径上都是 `PHASE6_DELIVERY_MERGE_UNPROVEN`。
- **已证明的 close 保留其证明。** 终态写入在同一事务里持久化 close 自身的关联事实（`delivery.proof`：target、tip、时间，以及需要时的已验证 commit）；只读 gate 信任该记录，而不是重读可能已被常规清理移除的 checkout，且任何调用方载荷都无法提供它。diff 经临时文件流式送入 `patch-id`，大交付只会因关联不成立而失败，不会因缓冲上限而失败。
- **已存记录保持可读。** 旧形状写入的快照保留其 `delivery.pr` 与自由文本 `merge` 作为历史：持久状态校验把这些成员视为不存在，而不是判整份快照无效（与改名前的 `branch.source` 同一种读兼容）。写路径依旧拒绝它们。
- **拒绝既说原因也给可执行恢复。** 明确区分失败的那条关联：交付分支无引用、tip 不在目标内、提交在上游没有 patch 等价副本、记录的 commit 不存在、或记录的 commit patch id 与交付 diff 不同；并指向：先在 plan checkout 内 fetch 目标分支、恢复交付分支引用、重试，或通过 `mstar workflow evidence` 记录 provider merge/squash commit。不新增任何网络/provider 调用，Git 读取全部沿用既有 argv 数组 helper。
- **已知边界写进文档而不是藏起来：** 无 merge commit 的 rebase 与单提交 squash 由 `git cherry` 自证（交付历史一旦含 merge commit，该捷径不适用，需记录 provider commit 或被拒绝）；多提交 squash 无法靠 patch 等价证明（逐提交 patch id 与合并后的单一 patch 不同），必须记录 provider commit；解决冲突后内容改变的 squash 没有本地证明，终态走 `mstar workflow lifecycle --status stopped|failed --reason`；目标在本地与远端都没有引用时是拒绝而非放行（单纯本地 head 滞后不算，因为先读远端引用）。legacy `completed` 快照会重新过门；最小恢复是用 `git worktree add` 重建记录的 checkout（gate 重证明是只读的）；持久恢复再加 `mstar workflow reopen`（只放行这类未证明历史）和一次普通 close，由它重新证明并持久化 proof。 已知边界如实说明：checkout 与交付分支引用都被清掉后，本地再无事实可重建关联，gate 拒绝保持——cleanup 合同保留 squash-only 本地分支，正是为了不让受支持的清理走到这一步。
- `mstar workflow evidence` 发布新形状（`merge { commit? }`：成员可选，但一旦提供就必须带 `commit`，CLI schema 现在同样要求；无 `pr`）与对应 help；随重复身份一起删除的还有锚点/PR 不一致的告警与 close 时的不变性拒绝。
