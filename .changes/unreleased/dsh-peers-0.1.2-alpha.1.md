- **dsh plugin**: `@deepseek-ai/dsh-*` peers upgraded to the `0.1.2-alpha.1` line (`^0.1.2-alpha.1`; `@deepseek-ai/cordis` stays `^4.0.1`; `dsh-llm-fallbacks` stays `^0.3.0` — its published 0.3.x peers are `^0.1.1-rc.x`, which excludes `0.1.2-alpha.1` prereleases), targeting NEW tag `dsh-v0.1.2-alpha.1` vs PREV `dsh-v0.1.1-rc.2` (compare: https://github.com/deepseek-ai/deepseek-harness/compare/dsh-v0.1.1-rc.2...dsh-v0.1.2-alpha.1). Verified against that diff: the two headline changes do not touch any surface this plugin consumes — the Remote cutover (client remotes now flow through `@deepseek-ai/dsh-api-remotes` and the api-controller generated `/remote` contributions; `dsh-host-apiproxy` stays host-side) and the `code-mode` → `ptc` tool-presentation rename (mode value `ptc`, `tools:ptc-only`, `tools/ptc-dispatch-log`; session-persistent vocabulary intentionally unchanged). The plugin has no proxy RPC callers and no code-mode references, so the only adapter change is the client-bundle purity allowlist: `dsh-host-apiproxy` dropped from `INLINE_SAFE` (remaining remotes route via the `GENERATED_REMOTE` `/remote` rule). `0.1.2-alpha.1` is not yet on the public npm registry (highest published is `0.1.1-rc.2`), so `bun.lock` stays on the rc.2 line until the prerelease lands.
