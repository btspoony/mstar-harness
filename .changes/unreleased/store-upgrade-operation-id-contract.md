- **`store upgrade` honours `--operation`, and refuses a malformed id before it advances the execution schema.** The caller's id is the idempotency key of the exact request, so a clean retry replays its retained reservation and receipt instead of minting a fresh operation; a retry that adds a request-identity option (`--ack-skip-workflow`, `--ack-skip-compass` or `--delivery`) is a different request and refuses `execution.operation-conflict`, which the option's own help now states instead of promising a same-id retry. `--ack-skip-dsh` is not part of that identity — it only disposes DSH host-state facts — so a retry that adds only it replays the already-committed execution half under the same id. The `store.upgrade-dsh-source-refused` recovery is not such a retry: its advertised retry also names the ids this invocation committed under `--ack-skip-workflow`, and those acknowledgements are request identity, so the full advertised retry must omit `--operation` (minting a fresh id) rather than reuse the old one under the widened skip set, or else replay the original request unchanged first. A malformed id is rejected at the entry of `upgradeStoreMinimal`, so only the execution schema advance and the execution authority are untouched by that refusal; the collaboration lane is not, because before that validation runs `store upgrade` advances an existing v1 lane, and on a fresh or file-era checkout it creates and publishes the scope's first collaboration lane, so a corrected retry resumes on collaboration authority this refused run already advanced or created.

- **`store upgrade` 遵守 `--operation`，并在推进 execution schema 之前拒绝非法 id。** 调用方的 id 是该确切请求的幂等键，因此干净的重试会重放既有预留与收据，而不再另生成一个操作；附带新的请求身份选项（`--ack-skip-workflow`、`--ack-skip-compass` 或 `--delivery`）的重试属于不同请求，以 `execution.operation-conflict` 拒绝——选项帮助现在写明这一点，而不再承诺同 id 重试。`--ack-skip-dsh` 不属于该身份——它只处置 DSH host-state 事实——因此仅附加它的重试会在同一 id 下重放已提交的 execution 部分。`store.upgrade-dsh-source-refused` 的恢复不属于这种重试：它宣称的重试还会列出本次调用通过 `--ack-skip-workflow` 已提交的 id，而这些确认属于请求身份，因此完整宣称的恢复重试必须省略 `--operation`（生成新 id），而不是在扩大后的 skip 集合下沿用旧 id；或者先原样重放原始请求。非法 id 在 `upgradeStoreMinimal` 入口即被拒绝，因此该拒绝不会触碰的只有 execution schema 推进与 execution 权威状态；但 collaboration lane 不受此保护，因为在该校验之前 `store upgrade` 就会推进既有的 v1 lane，而在全新或 file-era 的 checkout 上还会创建并发布本 scope 的第一个 collaboration lane，修正 id 后的重试是在本次被拒调用已经推进或创建的 collaboration 权威上继续。
