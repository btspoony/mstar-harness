- **`store upgrade` honours `--operation`, and on the normal upgrade path refuses a malformed id before it advances the execution schema.** The caller's id is the idempotency key of the exact request, so a clean retry replays its retained reservation and receipt instead of minting a fresh operation; a retry that adds a request-identity option (`--ack-skip-workflow`, `--ack-skip-compass` or `--delivery`) is a different request and refuses `execution.operation-conflict`, which the option's own help now states instead of promising a same-id retry. `--ack-skip-dsh` is not part of that identity — it only disposes DSH host-state facts — so a retry that adds only it replays the already-committed execution half under the same id. The `store.upgrade-dsh-source-refused` recovery is not such a retry whenever its advertised retry carries workflow acknowledgements: it then names the ids this invocation committed under `--ack-skip-workflow`, and those acknowledgements are request identity, so the full advertised retry must omit `--operation` and mint a fresh id rather than reuse the old one under the widened skip set. A recovery whose advertised retry carries no workflow acknowledgement stays a retry of the same request and can replay under the same id. A malformed id is rejected at the entry of `upgradeStoreMinimal` on the normal upgrade path. That rejection still leaves the collaboration lane moved, because before it runs `store upgrade` advances an existing v1 lane, and on a fresh or file-era checkout it creates and publishes the scope's first collaboration lane, so a corrected retry resumes on collaboration authority this refused run already advanced or created. The guarantee does not extend to a combined store whose collaboration rows still make `store upgrade` take the `collaboration.cutover-required` branch: that branch advances the execution schema and throws the cutover refusal before `upgradeStoreMinimal` is reached, so a malformed id there is refused by the cutover refusal alone, never by the id check.

- **`store upgrade` 遵守 `--operation`，并在常规升级路径上于推进 execution schema 之前拒绝非法 id。** 调用方的 id 是该确切请求的幂等键，因此干净的重试会重放既有预留与收据，而不再另生成一个操作；附带新的请求身份选项（`--ack-skip-workflow`、`--ack-skip-compass` 或 `--delivery`）的重试属于不同请求，以 `execution.operation-conflict` 拒绝——选项帮助现在写明这一点，而不再承诺同 id 重试。`--ack-skip-dsh` 不属于该身份——它只处置 DSH host-state 事实——因此仅附加它的重试会在同一 id 下重放已提交的 execution 部分。`store.upgrade-dsh-source-refused` 的恢复在宣称的重试带有 workflow 确认时不属于这种重试：此时它会列出本次调用通过 `--ack-skip-workflow` 已提交的 id，而这些确认属于请求身份，因此完整宣称的恢复重试必须省略 `--operation` 并生成新 id，而不是在扩大后的 skip 集合下沿用旧 id。宣称的重试不带任何 workflow 确认的恢复仍是对同一请求的重试，可以在同一 id 下重放。在常规升级路径上，非法 id 在 `upgradeStoreMinimal` 入口即被拒绝。但该拒绝仍会留下已推进的 collaboration lane：因为在该校验之前 `store upgrade` 就会推进既有的 v1 lane，而在全新或 file-era 的 checkout 上还会创建并发布本 scope 的第一个 collaboration lane，因此修正 id 后的重试是在本次被拒调用已经推进或创建的 collaboration 权威上继续。该保证不覆盖仍由 collaboration 行触发 `collaboration.cutover-required` 分支的合并存储：该分支会先推进 execution schema 并抛出 cutover 拒绝，早于到达 `upgradeStoreMinimal`，因此那里的非法 id 只被 cutover 拒绝挡下，从不经 id 校验。
