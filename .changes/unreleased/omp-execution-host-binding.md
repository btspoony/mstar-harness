- **The Phase-2 host observation now runs on the execution authority.** `mstar_coordinator` gained the two ACTIVE forms §6 defines — `{operation:"bind", workflowId, expected, operationId}` and `{operation:"recover", workflowId, priorSessionId, reason, attestation, expected, operationId}` — which call the existing `bindExecutionSession`/`recoverExecutionCoordinator` verbs directly under the host-derived `ExecutionIdentity`, while `show-recovery` answers from the DB workflow/session state on an ACTIVE root and keeps the unchanged Prepare view on the file route. The route is read from the addressed control root, never selected by a tool argument: a mixed or partial key set, an ACTIVE form on a pre-activation root and a Prepare form on an ACTIVE root all refuse before any IO. `expected`/`attestation` never travel back to the model.
- **`mstar_phase2.bind` carries no caller-supplied session path.** It takes `{operation:"bind", workflowId}` and adopts what the addressed root's own authority holds: on the ACTIVE route the session's DB coordinator binding (`ExecutionBinding`, resumed against the current epoch/root before it is recorded), on the pre-activation file route the workflow's OWN recorded coordinator envelope (resolved from the snapshot by the host, never supplied by the call). The durable binding record is now `{version:2, kind:"bind", …, executionBinding}`; earlier `coordinatorSessionPath` records stay readable as legacy history and are never upgraded into a DB binding, and an active binding always supersedes one.
- **The extra-primary launch journal is version 2 and takes `ExecutionLaunchAuthority`.** `reservePlanLaunch`/`recordPlanLaunch` resume the caller's `ExecutionBinding` before anything else, read the workflow's plans from `readExecutionAuthority` (never from the retired snapshot), and write under the §4.3 ladder — the maintenance exclusion (keyed through the engine's own `storeDbPath`, so it cannot drift) then the canonical workflow status lock — with `assertExecutionSessionCurrent` as the final synchronous check immediately before the atomic write. Reading an old journal is not writing it: adoption records the old bytes' digest and the old coordinator provenance and keeps every intent, state, target and evidence path. An owner or epoch change keeps unresolved intents occupied (`submitted`/`refused`/`uncertain` may be recorded by any currently bound coordinator as native transport evidence; a side-effecting `starting`/`created`/`submitting` only by the reserving session), and a stale or foreign binding never receives a duplicate intent.
- **New read-only host evidence producer (architecture contract §4.2).** `packages/omp/src/execution-host-inventory.ts` builds ONE carrying session's hidden history as ONE canonical document — `{version:1, protocol:"host-hidden-inventory-v1", workflowId, host:"omp", hostSessionId, export:{sha256, document:ExecutionHostHistory}}` — embedding H1's own export value with the digest of its exact bytes, so a consumer recomputes both instead of trusting a summary. `mstar_phase2 {operation:"export-history", workflowId}` returns those bytes and digests through the existing tool result; it opens no file, spawns nothing, binds nothing, declares no quiesced/complete coverage and manufactures no operator attestation (the operator's `ActivationAttestation` stays the stop/adoption boundary, checked downstream). A blank native identity, an H1 export refusal or a decoded record declaring another workflow refuses instead of producing a partial document.

- **Phase-2 host observation 现在运行在 execution authority 之上。**`mstar_coordinator` 新增 §6 规定的两个 ACTIVE 形式 —— `{operation:"bind", workflowId, expected, operationId}` 与 `{operation:"recover", workflowId, priorSessionId, reason, attestation, expected, operationId}` —— 在 host 派生的 `ExecutionIdentity` 下直接调用既有 `bindExecutionSession`/`recoverExecutionCoordinator`；`show-recovery` 在 ACTIVE root 上读取 DB workflow/session 状态，在 file route 上保持不变的 Prepare 视图。route 由被寻址的 control root 决定、绝不由 tool 参数选择：混合或字段不全的调用、在 pre-activation root 上使用 ACTIVE 形式、在 ACTIVE root 上使用 Prepare 形式，都会在任何 IO 之前拒绝。`expected`/`attestation` 绝不回传给模型。
- **`mstar_phase2.bind` 不再接受调用方提供的 session path。**它只接受 `{operation:"bind", workflowId}`，身份取自被寻址 root 自身的权威：ACTIVE route 上采用该 session 的 DB coordinator binding（`ExecutionBinding`，记录前先按当前 epoch/root resume），pre-activation file route 上采用 workflow **自身记录**的 coordinator envelope（由 host 从 snapshot 解析，绝不来自调用）。持久化 binding 记录现在是 `{version:2, kind:"bind", …, executionBinding}`；此前的 `coordinatorSessionPath` 记录仅作为 legacy history 可读，绝不升级为 DB binding，active binding 永远优先于它。
- **额外 primary 的 launch journal 升为 version 2，并改用 `ExecutionLaunchAuthority`。**`reservePlanLaunch`/`recordPlanLaunch` 首先 resume 调用方的 `ExecutionBinding`，从 `readExecutionAuthority` 读取 workflow 的 plan（绝不读已退役的 snapshot），并在 §4.3 锁阶梯下写入 —— 先 maintenance exclusion（键经引擎自身 `storeDbPath` 计算，不会漂移），再取 canonical workflow status lock —— 原子写入前的最后一步是同步的 `assertExecutionSessionCurrent`。读取旧 journal 不等于写它：adoption 记录旧字节摘要与旧 coordinator provenance，并保留每一条 intent、state、target 与 evidence path。owner 或 epoch 变更时未决 intent 继续占用（`submitted`/`refused`/`uncertain` 可由任一当前绑定的 coordinator 作为原生 transport 证据记录；有副作用的 `starting`/`created`/`submitting` 只能由 reserving session 记录），陈旧或外来的 binding 永远不会拿到重复 intent。
- **新增只读 host 证据产出（架构契约 §4.2）。**`packages/omp/src/execution-host-inventory.ts` 把**单个** carrying session 的 hidden history 构建为**单个** canonical 文档 —— `{version:1, protocol:"host-hidden-inventory-v1", workflowId, host:"omp", hostSessionId, export:{sha256, document:ExecutionHostHistory}}` —— 内嵌 H1 自身的导出值并给出其精确字节摘要，消费方据此自行重算而不是相信摘要。`mstar_phase2 {operation:"export-history", workflowId}` 通过既有 tool result 返回这些字节与摘要；它不打开文件、不 spawn、不 bind、不声称 quiesced/complete、也不制造 operator attestation（operator 的 `ActivationAttestation` 仍是 stop/adoption 边界，由下游校验）。native 身份为空、H1 导出拒绝，或 decoded 记录声明了另一个 workflow 时一律拒绝，绝不产出残缺文档。
