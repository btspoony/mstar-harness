- **The store's append-only ledgers are bounded.** A RUNNING workflow now retains at most `RUNNING_WORKFLOW_OPERATION_RECEIPT_LIMIT` (256) operation receipts: the cap is enforced in the same transaction that would insert a new non-terminal receipt, so overflow refuses `execution.receipt-retention-exhausted` and leaves no receipt, revision or effect behind. No replay key is ever evicted to make room — every retained operation id keeps its exact replay and changed-intent conflict behavior — and the refusal names its recovery (adopt or close the workflow under a new operation id, then start a new workflow). A terminal mutation stays exempt and its prune still keeps exactly the close receipt. The `notes.jsonl` ledger compacts at `WORKFLOW_NOTES_LEDGER_MAX_BYTES` (4 MiB) under the store's own `BEGIN IMMEDIATE` write lock, writing a same-directory temporary file, fsyncing, renaming atomically and fsyncing the directory; the newest complete lines that fit the read window are kept, the triggering note always survives whole, and a `workflow-notes-compaction` marker is written as the FINAL row with the dropped byte/line/record counts and the dropped prefix's sha256. Coverage reads a `WORKFLOW_NOTES_LEDGER_READ_BYTES` (1 MiB) tail window, drops the partial first line, and reports `readWindow: {offset, totalBytes, truncated}` plus `compaction` so a truncated read is disclosed instead of being reported as the whole ledger. The rewrite is published only while the ledger still holds the snapshot it classified: a lock-free peer frame that lengthened the leaf makes the compaction discard its temporary file rather than delete that frame, and the ledger is simply retried past the ceiling on the next such append. Every earlier marker is dropped too and counts toward the disclosed dropped bytes, so exactly one marker survives as the final row. That row stays inside the read window until later appends push the ledger past it; coverage then reports a truncated window with `compaction: null` rather than resurfacing the older disclosure. The codex `.bak` growth recorded beside these two surfaces was already bounded to one backup per install; no code change was needed there.

- **store 的追加式台账现在有明确上限。** 运行中的工作流最多保留 `RUNNING_WORKFLOW_OPERATION_RECEIPT_LIMIT`（256）条操作回执：该上限在“插入新的非终态回执”的同一事务内校验，超限即以 `execution.receipt-retention-exhausted` 拒绝，且不留下任何回执、修订或副作用。引擎绝不会为腾空间而丢弃回执（每个保留的 operation id 的重放与变更意图冲突语义完全不变），拒绝文本同时给出恢复路径（用新的 operation id adopt/close 该工作流，然后为新工作新建工作流）。终态变更仍然豁免，其裁剪仍只保留 close 回执本身。`notes.jsonl` 台账在超过 `WORKFLOW_NOTES_LEDGER_MAX_BYTES`（4 MiB）时，在 store 自身的 `BEGIN IMMEDIATE` 写锁下压缩：同目录临时文件、fsync、原子 rename、再 fsync 目录；保留能放进读窗口的最新完整行，触发本次压缩的 note 始终整条保留，并以 `workflow-notes-compaction` 标记作为最后一行，记录被丢弃的字节/行/记录计数与该前缀的 sha256。coverage 只读 `WORKFLOW_NOTES_LEDGER_READ_BYTES`（1 MiB）尾部窗口，丢弃被截断的首行，并返回 `readWindow: {offset, totalBytes, truncated}` 与 `compaction`，因此被截断的读取会被明示，而不会被当作整份台账。只有当台账仍保持被分类的那份快照时才会发布重写：无锁 peer 帧使文件变长时，压缩会丢弃临时文件而不是删掉那一帧，并在下一次越过上限的追加时再试；所有旧标记也会一并剔除并计入已披露的被丢弃字节，最终只保留一个作为末行的标记。该标记会一直留在读窗口内，直到后续追加把台账推出窗口；此后 coverage 会报告被截断的窗口且 `compaction` 为 null，而不会重新浮现更早的披露。同一问题中记录的 codex `.bak` 增长此前已收敛为每次安装一份备份，无需改动代码。
