- **ONE shared MCP connection; the per-agent scoped mount is gone.** The dsh bundle's `mstar-mcp` row is the whole MCP channel for the host: the plugin registers no MCP client of its own, and a subagent shares the connection its parent already has. A per-agent instance could never carry per-call arguments (a dsh gate cannot rewrite tool arguments), so it bought no capability — only one Node process per agent.
- **The control root is DECLARED, never inferred.** It resolves in one ordered rule: the launch pin (`mstar mcp --harness <absolute path>`, else a non-blank `MSTAR_HARNESS_DIR`), then the admitted call's `harness` field; `harness.scaffold` keeps its null-root bootstrap exception, the commands whose contract reads no control root (`schema`, `path.resolve`, `host.*`, `doctor`, the read-only validators) run with a null root instead of being refused, and every other call that declares no root is refused with `[mcp.control-root-unresolved]` naming the cause and the recoveries — the two launcher ones are universal, the per-call `harness` selector is tool-dependent. The launch cwd is the HOST's directory and is no longer a root candidate anywhere — adopting it would root writes on an unrelated project. A pin beats a per-call `harness`, and the invocation workspace now anchors on the root actually used, so cwd-derived paths land under the declared harness.
- **On an unpinned connection `harness` is REQUIRED** on every published tool whose root is not otherwise fixed, so a caller cannot omit the one fact the root resolution needs; a pinned connection keeps the field optional, since the pin is the default.
- **A declared root selector IS the call root, pinned or not.** On an unpinned connection every root selector a command declares reaches the resolver as that call's root — including a non-`harness` one such as `sdd.workspace`'s `controlRoot`, which the transport accepted but never forwarded, so that action refused with `mcp.control-root-unresolved` although the caller named a real root. A pinned connection still replaces `harness` with the pin and removes every other root selector, so the pin keeps deciding.
- **An omitted `harness` on a union input is reported together with the fields admission already refused**, never instead of them, so one response names every problem.
- **An operation TARGET is an explicit input too.** `store.execution.export` / `restore-preview` / `restore` require an absolute `harness` naming the store they read or restore, and `path.resolve` requires its start `path` when the connection declared no root: neither is discovered from the launch directory, so an omitted target can no longer read — or, for `restore`, write — the host checkout's own store. Both refusals name the field and the recovery.
- **The MCP-only identity wiring is retired from the CLI (`mstar mcp`).** `--identity-env`, the declared-identity lock, selector stripping and the connection-wide default session id are all gone. The connection carries no identity and by default accepts none from a caller either: a call that supplies `sessionId` is refused with `mcp.caller-identity-unavailable`, and only an explicit launch opt-in (`mstar mcp --trust-caller-session-id`, OFF in the shipped row) publishes the selector. That refusal is aggregated with the call's other input diagnostics, so one response reports every problem. An operation that NEEDS a session identity runs on the dsh native command surface, where it comes from `exec.agent.id`, or through the CLI — the native tools cover plan bind, audit report validation and execution clear only, so plan prepare/progress/complete are CLI-only today.

- **整个宿主只共享一条 MCP 连接；按 agent 的 scoped mount 已移除。** dsh bundle 的 `mstar-mcp` 行就是宿主的全部 MCP 通道：插件不自行注册任何 MCP client，subagent 共用父级已有的那条连接。按 agent 的实例本来也拿不到按调用参数（dsh 闸门无法改写工具参数），因此换不来任何能力——只会每个 agent 多一个 Node 进程。
- **control 根是「声明」出来的，绝不推断。** 它按一条有序规则解析：启动钉（`mstar mcp --harness <绝对路径>`，否则非空的 `MSTAR_HARNESS_DIR`），再是被准入这次调用的 `harness` 字段；`harness.scaffold` 保留其空根 bootstrap 例外，契约不读取 control 根的命令（`schema`、`path.resolve`、`host.*`、`doctor` 与只读校验器）改为以空根运行而不是被拒绝，其余未声明根的调用一律以 `[mcp.control-root-unresolved]` 拒绝，并点名原因与恢复路径——两条启动方恢复路径对任何命令都成立，按调用的 `harness` 选择器则依工具而定。启动 cwd 属于**宿主**，不再是任何候选根——采用它会把写入落到不相干的项目上。连接钉优先于按调用的 `harness`，且调用工作区现在锚定在实际使用的那个根上，因此由 cwd 派生的路径落在已声明的 harness 下。
- **未钉的连接上 `harness` 为必填**：凡是根不另有来源的已发布工具都如此，调用方无法漏掉解析所需的这唯一事实；已钉的连接保持该字段可选，因为钉本身就是默认值。
- **声明的根选择器就是本次调用的根，无论是否已钉。** 未钉的连接上，命令声明的每个根选择器都会作为本次调用的根传给解析器——包括非 `harness` 的选择器（如 `sdd.workspace` 的 `controlRoot`）：此前它被接收却从不转发，于是即使调用方点明了真实根，该 action 仍以 `mcp.control-root-unresolved` 拒绝。已钉的连接仍会用钉覆盖 `harness` 并移除其他根选择器，钉继续说了算。
- **union 输入漏写 `harness` 时，它与准入已拒绝的字段一并上报**，绝不互相替代，一次响应即列出全部问题。
- **操作 TARGET 同样是显式输入。** `store.execution.export` / `restore-preview` / `restore` 要求用绝对路径 `harness` 指明要读取或恢复的那个 store；连接未声明根时 `path.resolve` 也要求显式传入起始 `path`：两者都不再从启动目录推断，因此漏写 target 既不会读到、也不会（对 `restore`）写到宿主检出自身的 store。两处拒绝都点名字段并给出恢复路径。
- **仅属 MCP 的身份接线已从 CLI（`mstar mcp`）退役。** `--identity-env`、已声明身份锁、选择器剥离与连接级默认 session id 全部移除。连接不携带身份，默认也不接受调用方声明的身份：传入 `sessionId` 的调用以 `mcp.caller-identity-unavailable` 被拒绝，只有显式启动开关（`mstar mcp --trust-caller-session-id`，随发行的行中为 OFF）才会发布该选择器；该拒绝与本次调用的其他输入诊断合并上报，一次响应列出全部问题。**需要**会话身份的操作走 dsh 原生命令面（身份来自 `exec.agent.id`）或走 CLI——原生工具只覆盖 plan bind、审计报告校验与 execution clear，故 plan prepare/progress/complete 目前只能走 CLI。
