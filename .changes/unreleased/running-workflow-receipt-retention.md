- **A running workflow's operation receipts are no longer count-capped.** `execution.receipt-retention-exhausted` and the exported `RUNNING_WORKFLOW_OPERATION_RECEIPT_LIMIT` constant are gone, with no compatibility shim: a RUNNING workflow refused its next ordinary plan or workflow operation once it retained 256 receipts, and the only recovery it named was to close or adopt the workflow and start a new one — a route an unfinished lifecycle cannot take without discarding the work it still holds. Every retained receipt is a replay anchor, so the engine never evicts one to make room. Retention is therefore logical and lifecycle-scoped rather than numeric: each committed operation of the active lifecycle keeps one receipt row — its persisted replay metadata plus the recorded result payload where the writer stored one, while slim receipts persist the replay address and reconstruct the live state under the same epoch instead of recording a full result. That set grows with the operation count and the payloads actually stored until the workflow terminates, at which point the terminal mutation prunes it to exactly its own receipt. No supported in-place epoch advance bounds a running lifecycle's receipts: restore deliberately preserves prior-epoch receipt rows as history, outside the current epoch's replay scope, and the epoch delete in the create-only initializer can never remove receipts because that transaction refuses a non-empty execution domain. The terminal prune is a SQL `DELETE` that bounds what the store serves; it promises neither constant space nor a smaller SQLite file on disk. Exact replay, changed-intent conflicts, CAS, authorization and normal terminal behavior are unchanged.

- **运行中工作流的操作回执不再有数量上限。** `execution.receipt-retention-exhausted` 与导出的 `RUNNING_WORKFLOW_OPERATION_RECEIPT_LIMIT` 常量均已移除，且不提供兼容层：此前 RUNNING 工作流在保留 256 条回执后，会拒绝其下一条普通计划或工作流级操作，且给出的唯一恢复路径是关闭或收养该工作流再新建——未完成的生命周期无法采用，因为那会丢弃它仍然持有的工作。每条保留回执都是重放锚点，引擎绝不会为腾空间丢弃任何一条。因此保留是逻辑上的、按生命周期界定的，而非按数量：活动生命周期中每个已提交操作保留一行回执——写入方持久化的重放元数据，以及在写入方保存了完整结果时的记录结果载荷；其中 slim 回执只持久化重放地址，并在同一 epoch 下重建实时状态，而不保存完整结果。该集合随操作数量与实际保存的载荷增长，直到工作流进入终态——终态变更会把集合裁剪为恰好它自己的回执。没有任何受支持的就地 epoch 推进能为运行中的生命周期界定回执数量：restore 会刻意把先前 epoch 的回执行作为历史保留，且位于当前 epoch 的重放范围之外；而仅用于创建空域的初始化事务中的 epoch 删除也不可能移除回执，因为该事务在任何回执行存在时即以非空域拒绝。终态裁剪是 SQL `DELETE`，只界定 store 对外提供的内容，既不承诺常数空间，也不承诺 SQLite 文件在磁盘上变小。精确重放、变更意图冲突、CAS、授权与正常终态行为完全不变。
